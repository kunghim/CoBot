## 2026-10-13 第一轮：方向与地基

参考材料：multibot 的需求技术方案、协调者设计、M4 审批网关调研与已知限制；Grok Bot 调研（工作站来源：`research/platforms/grok-bot-xai/README.md`）及其多项目开发方案（工作站来源：`research/platforms/grok-bot-xai/多项目开发方案.md`）；Orca × Codex CLI 交互机制（工作站来源：`research/github/orca-stablyai/codex交互机制.md`）。

### 产品定位

- **开源，前期自用。** V1 先满足自用，但不写只能在作者本机运行的代码，避免开源时推倒重来。
- **V1 只做软件开发场景。** Codex 的强项是读写代码、跑命令、在沙箱里试错；办公、学习类角色用不上这些，更适合用便宜的模型。multibot 后期扩到 5 个场景、16 个角色，cobot 先收窄，等底座稳定再扩。
- **V1 验收标准是用 cobot 开发 cobot 自己。** 这条链路覆盖拆任务、并行开发、测试、审查、审批、合并，能检验底座是否真的可用。

### 地基（来自 multibot 的经验）

- **接入方式换成 `codex app-server`。** multibot 每轮起一个一次性的 `codex exec` 进程；为了在无人值守时做审批，只能把 Codex 关进只读沙箱，再用网关工具重做写文件和跑命令，结果原生能力被削掉一块，约束主要靠提示词。app-server 常驻在线、走 JSON-RPC，执行命令或改文件前会向宿主请求批准，还支持中途打断和追加指令；Orca 就是这样接入 Codex 的。待在本机 Codex 版本上做小验证后定稿。
- **协作动作做成 MCP 工具。** multibot 让主 Agent 在回复里写 `dm:角色` 代码块再由后台解析，代码块没闭合就会漏给用户，提示词还得专门教格式。改由 cobot 后台提供结构化工具，便于审计。multibot 的审批网关已经证明后台充当 MCP 服务可行。
- **以任务为中心，而不是以聊天为中心。** multibot 的进度散落在聊天记录和交接卡里。参考 Grok Bot 官方多项目实践：每个任务只有一个负责人，有完成标准和证据，状态记在任务板上，聊天只做讨论和交接，bot 记忆只存工作方法和偏好。
- **并行编码要隔离。** 多个开发 bot 同时改同一目录必然冲突；每个编码任务用独立分支和 git worktree，合并前由审查 bot 和用户把关。multibot 没有这一层。
- **凭据只留一份，不进项目目录。** 起因：multibot 冒烟测试时，在 Windows 上把 Codex 登录凭据复制进了仓库内的数据目录，且该目录没有被 git 忽略。多个 bot 怎么共享登录，放到技术方案阶段再定。
- **沿用 multibot 的分工原则。** Codex 管任务内部，cobot 管 bot 之间（身份、记忆、派活、审批、成本）。

### 协作与运行方式（用户回答）

- **协作形态。** 支持私聊与群聊。每个项目创建时自动分配一个主 Agent，权限大于其他 bot；其他 bot 可以互相聊天，也可以和主 Agent 聊天；任何 Agent 都不能跨项目聊天。最初的建议是只由主 Agent 调度、bot 之间不直接对话，用户选择支持 bot 之间直接对话。由此带出主 Agent 权限、自由聊天护栏、群聊运转、记忆隔离等待定问题。
- **V1 不做无人值守。** 定时任务、事件触发、后台常驻、开机自启都不做。暂时理解为：任务在 cobot 运行期间执行，用户不盯着也会继续跑完（待用户确认）。
- **只在本机运行。** 保留「后台服务 + 网页界面」分层，以后要上服务器不用重写。
- **引擎预留 Claude Code 和模型厂商 API，V1 只接 Codex。** 两类扩展差异很大：Claude Code 自带工具循环，接入方式与 Codex 类似，cobot 只需路由消息、处理审批；模型厂商 API 只提供模型，工具调用循环要由 cobot 自己驱动，或者限定这类 bot 只做讨论、评审类角色。因此 cobot 内部的消息、工具调用、审批请求和用量格式都要与具体引擎无关。

### 其他

- multibot 是第一版原型，用户已验证可行；cobot 新起，multibot 只作参考，收尾时备份并清理。
- cobot 仓库已由用户建好；需求定稿后迁入，克隆位置届时按 `computers/CLONE.md` 确认。

## 2026-10-13 第二轮：协作细则

### 主 Agent 与成员

- **主 Agent 有权创建合适的 bot，因此能看到完整的内置角色库**（用户定）。其他 bot 只知道本项目已经创建了哪些成员；主 Agent 新建 bot 后要通知它们。
- **补充（用户授权按设计补充）：**
  - 创建只从内置角色库里选，受项目成员上限约束（默认沿用 multibot 的 6 个），每次创建都要用户批准。（本条起初误记为不需要批准，第三轮用户更正：主 Agent 只是拥有这项权限，实际创建仍须用户批准。）
  - 通知方式：新的成员名单在每个 bot 下一轮开始时带入，不为此单独唤醒空闲 bot，避免白烧 token。
  - 只有主 Agent 能建任务、拆任务、指派负责人；bot 可以更新自己负责的任务、提交证据、提议新任务，也可以把自己的任务转交给另一个 bot，对方接受后生效，任务板留痕并通知主 Agent。
  - 主 Agent 负责群聊秩序；不能替用户批准高风险操作，也不能自行合并分支。

### 审批

- **bot 的审批卡可以传导到主 Agent 会话，用户在那里直接审批；一个 bot 的审批请求不会同步给其他 bot**（用户定）。
- **补充：** 卡片同时出现在发起 bot 的会话和用户与主 Agent 的会话，任一处批一次即生效；卡片只给用户看，不进主 Agent 和其他 bot 的上下文；审批结果作为客观记录写进对应任务。

### 轮次控制（用户定）

- bot 之间连续协作的轮数默认上限 6，用户可以调大。
- 到达上限时不直接暂停，而是请用户审批是否继续；用户批准后重新计数。
- 上限之前设风险区，例如上限 10 轮时从第 8 轮开始：由小模型判断下一步是否有必要让用户审批，原本不需要审批的步骤也可以被要求审批。这样停下来时不总是机械地问「是否继续」。
- 用户最初设想让这类卡片「伪装成智能体认为下一步有安全风险」。建议改为照实写理由，并把卡片分成「安全审批」和「协作确认」两类、进同一个审批队列。理由：审批卡也是审计记录，理由失真会误导事后排查；频繁出现名不副实的「安全风险」会让用户习惯性点通过，削弱真正的安全审批。待用户确认。
- 一轮怎么计数待确认。建议：协作链从用户的一条消息或一次批准开始，之后每当某个 bot 因其他 Agent 的消息、@ 或交接被唤醒，记一轮；用户插话或批准继续后清零；bot 一轮内部的工具调用不计。

### 群聊（用户定）

- 一个项目一个群，群成员要受限，不设全员群。
- @ 谁谁回答；不知道 @ 谁就 @ 主 Agent，由主 Agent 决定，主 Agent 可以转问用户。没有 @ 的消息按 @ 主 Agent 处理。
- 群成员上限与拉人规则待确认。建议：用户和主 Agent 固定在群里，另外最多 3 个 bot（可调），由主 Agent 按需拉人或移出，用户也可手动调整。

### 记忆（用户定）

- 先按项目隔离，后续需要再改。跨项目的全局偏好暂不做。

### 其他

- 第一轮对「不做无人值守」的理解（cobot 运行期间任务会继续跑完），用户未提异议，按此执行。

## 2026-10-13 第四轮：消息持久化与崩溃恢复

- **采纳 G20：消息先写数据库，再主动唤醒。** bot 之间的消息、交接、群聊发言请求、审批，都先写进数据库，再主动唤醒目标 bot；目标在忙就排队，等它这一轮结束再送；后台重启后继续送还没送达的；按编号去重。依据：逆向显示 Grok Bot 是「服务端先存、主动投递、送到即唤醒」，不是让对方轮询；Orca 是「放进邮箱、提醒对方来取」。cobot 只有一个本地后台，可以同时做到不丢和即时。
- **崩溃恢复是硬要求（用户定）。** cobot 基于 Codex，指令一旦发给 Codex，即使 cobot 自己崩溃，Codex 也可能继续运行。重启后必须知道哪些消息还没处理、哪些中断了、该怎么处理，只有把状态存进数据库才做得到。
- **建议的做法（待确认，原 V1 功能清单第 11 节，现见[需求文档](需求文档.md)第 13 节）：** 每一步先记再做；重启后把数据库里进行中的工作与 Codex 自己的线程记录、任务分支里的改动逐一对账；跑到一半中断的轮次不自动重跑，交给用户选择。
- **待定：cobot 退出时 Codex 进程随之停止，还是继续运行。** 建议 V1 随 cobot 一起停，理由是审批、轮次上限和预算都由 cobot 把关，cobot 不在时让 Codex 继续干等于这些规则失效。三项事实放进计划中的 app-server 小验证一起测：cobot 被强制结束后 Codex 进程是否退出；它启动的命令是否还活着；重启后能否从线程记录判断最后一轮有没有跑完。

## 2026-10-13 第五轮：用 hook 和 MCP 实现崩溃降级（讨论中）

- 用户提出用 MCP 或 hook 机制处理「cobot 崩溃时 Codex 停不停」。核实了 Codex 0.161.0 的 hook 能力（依据源码），整理为候选方案：[Codex hook 能力核实与崩溃降级方案](参考/Codex-hook与崩溃降级.md)。
- 核心结论：Codex 的 hook 出错、超时、MCP 连不上时一律放行，只有明确返回拒绝才拦截。所以安全闸门必须是「命令类型 hook 在本地读 cobot 的租约文件，判定不在线就主动拒绝」，不能靠「连 cobot，连不上算拦截」。
- 候选方案把上一轮的「停还是不停」变成「不停，但 cobot 不在时降级」：Codex 还能思考和读文件，但改不了文件、跑不了命令、发不了消息；一轮结束时由 hook 把结果记到本地日志，供 cobot 重启后对账。同一份租约文件还能在 cobot 在线时硬性执行暂停、预算、轮次上限和目录边界。
- 待确认：是否采纳；连同 app-server 小验证一起测 5 项前提（见方案文档末尾）。
- **用户补充：hook 连不上 cobot 时，把事件写进约定文件，cobot 启动后读取。** 已并入候选方案，作为「事件转发与降级落盘」，并补充落盘目录的设计：按 bot 分目录、一事件一文件、按事件编号去重、只记元数据并脱敏、设总量与保留期上限、cobot 不在线时直接落盘、启动时导入。Orca 的 hook 采用同样做法。降级逻辑必须写在命令类型的 hook 脚本里，MCP 类型的 hook 连不上时没有机会执行我们的代码。
- **用户同意：「不停但降级」方向已定**，细节等 app-server 小验证结果再定。

## 2026-10-13 第六轮：去掉「项目」概念，暂缓群聊

- **不设「项目」，直接创建 main bot 和协同 bot（用户定）。** 创建 main bot 时选择工作目录，可以同时选协同 bot；创建后用户也可以自己引入新的协同 bot。参照 Grok Bot：它没有项目概念，甚至没有目录概念；cobot 是本地编码工具，所以保留工作目录。

- **群聊暂缓，V1 不做（用户定）。** 理由：bot 之间已经能互相私聊，群聊只是把内容放到一起。第二、三轮关于群聊的决定（成员上限、@ 路由）保留在本日志里，以后做群聊时再用；借鉴清单的 G1 随之暂缓，G2「明确不回复」仍可用于 bot 之间的私聊。
- **侧边栏（用户定）：** 只显示 main bot，协同 bot 挂在对应 main bot 下面，在菜单上体现从属关系。
- **待确认：同一个目录能否创建多个 main bot。** 建议 V1 一个目录只对应一个 main bot，避免两组 bot 同时改同一个仓库。

## 2026-10-13 第八轮：界面布局草案（待确认）
