# 升级与回滚说明

- 适用：独立 `cobot` 可执行文件（server 目标，内嵌前端与迁移）。桌面壳升级同版本辅助 `cobot`，另行说明。
- 数据位置：生产 `~/.cobot`，开发 `~/.cobot-dev`；升级不迁移目录、不改团队工作目录。

## 升级前

1. 在运行终端按 Ctrl+C，等待 `stopped`，确认实例正常退出后再替换程序；同 profile 不允许并存第二个调度器。强制结束进程属于异常退出，会保留未知执行等待核对。
2. 备份数据根（整个目录即可，核心是其中的 SQLite 库）：

```bash
cp -r ~/.cobot ~/.cobot-backup-$(date +%Y%m%d)
```

3. 记下当前版本：`cobot version`。

## 升级

1. 用新可执行文件替换旧文件（Windows 直接覆盖；先确认旧进程已退出，否则文件被占用）。
2. 启动：`cobot serve --profile production`。**数据库迁移在启动时自动执行**，无需手工步骤；已有业务库升级前，由 CoBot 使用 SQLite `VACUUM INTO` 在数据根的备份目录生成一致快照，再由内嵌 goose 迁移向前升级。失败不提供业务、不自动降级。
3. 打开终端打印的一次性链接确认页面可授权、团队可选、消息可发。

运行期 `runtime/instance.lock.guard` 由操作系统锁定，正常退出后该空文件仍可保留；不要通过删除它解除正在运行的实例锁。发现记录与凭据由当前持有者清理，异常退出后的 OS 锁会随进程释放。升级前仍须正常停止旧程序，不混用新旧锁协议的运行实例。

## 回滚

- 迁移是**向前**的：一旦新版本写入了更高 schema 版本，旧可执行文件会**拒绝打开该库**（"database schema version N is newer than supported"），这是刻意的保护，避免旧程序误写新结构。
- 因此回滚的正确做法是**恢复升级前的备份目录**（覆盖回 `~/.cobot`），再运行旧版本；不要试图让旧二进制直接打开新库。
- 若新版本启动即失败且未完成任何业务写入，用备份覆盖即可，代价是丢失升级后这一小段新数据。

## 桌面壳

- 桌面壳与同版本 `cobot` 配套；本轮未做原生签名/公证，也未验证 macOS 运行（见支持矩阵）。桌面升级应整体替换，不混用版本。

## 签名与公证

- 本轮未做代码签名与公证；从非受信渠道获取的可执行文件需自行核对 [依赖清单](依赖清单.md) 与 `scripts/build.*` 产出的 sha256 校验值后再使用。许可证在公开发布前由用户确定。
