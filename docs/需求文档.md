## 1. 定位、目标与边界

**已确认。** CoBot 是开源、本地运行的通用多智能体协作应用。用户围绕目标组织队长与成员，分工、沟通、交接、验证和交付，也可以直接与任何成员沟通。编程是首版场景，不是产品的永久定位，后续可扩展办公、学习、创作等场景。

**职责边界已明确。** CoBot 提供客户端、协作编排与状态管理，整理角色、任务、上下文及相关资源后发给外部 Agent。Codex、Claude Code 等完整 Agent 执行文件操作、命令、Git、办公工具等业务动作。CoBot 不需要内置 Git 管理模块，团队需要选择工作目录，该目录不要求是 Git 仓库；仍负责可信成员身份、任务归属、消息投递、审批路由、预算和持久状态。

后端采用 **Go**。产品支持 Windows、macOS 客户端和浏览器访问本机服务；桌面壳、前端框架、数据库及发布顺序继续讨论。首版先接 Codex，适配层为其他完整 Agent 留出空间。仅模型 API 不等同于完整 Agent，其执行循环不默认由 CoBot 重做。

**本地运行范围已明确。** 不建设 CoBot 云端业务服务，不规划云执行、自托管远程业务服务或多机协同。服务器只可能用于安装包和必要资源分发；外部 Agent 自身使用的模型服务不属于 CoBot 云端业务服务。

首版目标是**用 CoBot 开发 CoBot 自己**：真实完成拆任务、成员实现、测试、审查、用户授权交付，再用交付后的版本继续下一项工作。开发与生产使用的配置、数据及运行入口应隔离；开发测试时可以只打开开发环境服务，通过 Web 检查和操作，不要求同时运行生产实例。

**首版暂不实现：** 群聊；定时任务、事件触发和开机自启；跨团队聊天、记忆与成员共享；Claude Code 的实际接入；办公、学习、创作角色模板；独立成果库；界面编辑角色文件。未来功能不提前摆空入口。

CoBot 运行期间，已启动任务可以在用户没有持续盯着页面时推进；需要输入或审批时仍等待用户。当前产品尚未实现，接入实验不等于首版验收完成。

## 3. 团队、工作区与保存位置（R01）

**已确认。** CoBot 的默认工作区位于 `~/.cobot`。用户创建团队时填写名称、选择工作目录，可勾选初始成员，队长自动产生；之后可继续引入成员。新建界面不要求轮数、风险区或 token 预算。

| 位置 | 职责 |
| --- | --- |
| `~/.cobot` | CoBot 的默认工作区；内部目录划分仍待设计 |
| 用户选择的工作目录 | 团队的共享工作上下文，可用于编程、办公、学习等场景，不要求是 Git 仓库 |
| 所选目录内的 `.cobot` | 保存与 Codex 等外部 Agent 交互有关的资源信息，并保留目录识别所需信息；资源格式和子目录待设计 |
| 成果保存位置 | 外部 Agent 按任务及用户指示保存成果，可以与团队工作目录不同 |

**已确认。** 所选工作目录的信息对队长及所有成员可见，由 CoBot 提供给各自的 Agent 上下文；不能只让队长知道。编程任务采用独立 worktree 时，仍保留团队目录信息，并记录具体任务的实际工作位置。界面的目录展示沿用集中展示规则。

所选目录内创建 `.cobot`，其中资源不自动纳入 Git 提交。已有 Git 仓库沿用本地排除机制，不修改共享 `.gitignore`；普通目录不要求初始化 Git。CoBot 管理自身交互资源，Git 和其他业务操作仍交给外部 Agent。

**沿用已确认的目录绑定规则。** 一个工作目录只属于一个团队，禁止嵌套绑定；CoBot 持久记录是绑定的事实来源，删除目录内 `.cobot` 不解除绑定。

| 情况 | 期望行为 |
| --- | --- |
| 同目录的大小写、斜杠或链接写法不同 | 按真实位置识别同一目录，避免重复团队 |
| 新目录包含或位于已绑定目录内 | 拒绝嵌套绑定，说明涉及的团队 |
| 有绑定但 `.cobot` 被删除 | 拒绝重复创建，可重建识别信息；实际丢失的资源须报告 |
| `.cobot` 存在但本实例无对应团队 | 不自动接管，由用户选择接管为新团队或取消 |
| 目录副本带有仍绑定另一位置的团队编号 | 按复制目录处理，用户接管为新团队后更新识别信息 |
| 已绑定目录不见了 | 标明目录丢失，不启动该团队成员，由用户重新指定位置 |
| 新位置携带同一个团队编号 | 按搬家更新绑定，仍检查重复及嵌套 |

团队支持列表、归档与删除；删除团队解除目录绑定，不授权删除用户文件。归档/删除时活跃任务、审批和交接的处理次序、交互资源清理策略仍待讨论，不能顺带清理项目或成果。

指定成果位置不自动扩大写权限，外部引擎仍须支持相应访问范围及审批。默认工作区内部划分、资源内容/生命周期及成果交付细则继续讨论。参考产品证据见工作区与保存位置调研（仅本机归档，非必读）。

**验收条件：** 创建团队必须选择目录；所有成员获得相同团队目录信息；目录内存在 `.cobot` 且不被自动提交；非 Git 目录可使用；删资源目录不绕过唯一绑定；目录失效不会静默换到其他位置执行；删除团队不删除用户文件。

## 4. 队长、成员与权限（R02）

**已确认。** V1 的五种内置成员角色是产品经理、前端开发、后端开发、测试工程师、代码审查。队长单独承担协调职责，不算这五种专业角色之一。

| 动作 | 用户 | 队长 | 成员 |
| --- | --- | --- | --- |
| 引入内置角色 | 可直接操作 | 可申请，每次必须获用户批准 | 无此权限 |
| 查看角色库 | 可供选择 | 完整内置库 | 只知道本团队已存在的成员 |
| 创建、拆分与指派任务 | 可直接管理任务板 | 可执行 | 可提议，不可自行建任务或指派 |
| 更新任务与提交证据 | 全部任务 | 协调与管理 | 自己负责的任务 |
| 转交自己的任务 | 可管理 | 可协调 | 可发起，对方接受后生效 |
| 批准高风险动作 | 可 | 不可代批 | 不可代批 |
| 批准合并（编程场景） | 决定是否合并 | 不可代批；获授权后可委托执行 | 不可代批；获授权后可执行 |

各 bot 创建、恢复及下一轮开始前获得团队工作目录信息；名单变化时带入最新名单，不额外唤醒空闲成员。用户可移除成员；**建议：** 移除前先转交任务。成员上限默认 6 是历史建议，是否包含队长尚需澄清。角色文件可由用户编辑，界面编辑留到以后，这是实现建议而非已冻结格式。

**验收条件：** 队长招募未批准不产生可运行成员；用户直接引入无需重复审批；其他成员下一轮拿到新名单；成员不能越权指派或批准合并。

## 5. 对话、沟通与唤醒（R03）

**已确认。** 用户可与队长或任意成员直接对话；成员之间、成员与队长之间可双向沟通，用户可查看全过程。不同团队间不可聊天、发消息或共享成员。

用户会话放在中间区域；bot 间沟通称“协作记录”，放在当前 bot 的右侧工作面板。当前界面草案采用只读查看，想插话就给对应 bot 发消息。V1 不做群聊，不沿用早期的群人数、@ 路由规则。

协作动作由 CoBot 的结构化工具完成：发消息、交接任务、汇报完成、向用户提问。消息先存入数据库，再主动投递并唤醒目标；目标忙时排到当前轮结束后；重启后续送确定未发送的消息，对已发送但结果未知的消息先对账，按编号去重。不能用回复中的特殊代码块作为通信协议。

**建议：** 把发送与运行状态分开；请求返回已收下、已送达、重复、对象不存在、无权限或不可用等客观状态，具体枚举未冻结。用户在工作中追加消息如何排队、打断或引导，仍待讨论。

**验收条件：** 发给别的团队被服务端拒绝；目标忙时消息不丢；已投递消息重放不重复启动同一工作；协作结论可回写任务。

## 6. 任务与交接（R04）

**已确认。** 任务有唯一负责人、描述、完成标准、证据和父任务；资源位置与结果版本按场景关联，不强制 Git 分支。聊天用于讨论，任务板记录进展和结论，记忆不替代任务资料。

**建议的状态：** 待办、进行中、待审查、完成；阻塞必须说明谁需要回答什么。需要输入是否是独立状态、还是任务标记，待讨论。完成时附与任务相符的证据，例如编程的测试/变更/审查、文档文件及版本、学习材料与结论。首版先实现编程流程，通用字段不绑定代码。

成员转交自己任务，对方接受后生效，任务板留痕并通知队长；接受前原负责人保持责任。用户可直接操作任务板。代码实现、测试、审查的任务依赖应明确表达。

**验收条件：** 交接中不会出现零个或两个负责人；对话约定写回任务；不能仅凭“已完成”的聊天消息认定验收通过。

## 7. 编程场景的隔离、测试、审查与合并（R05）

**已确认方向。** 编程场景并行修改需隔离；已有方案使用独立分支和 Git worktree，完成后测试、审查，由用户批准合并。这不是所有团队必须有 Git 的理由。

**职责修正。** 创建分支/worktree、查询差异、测试、提交、合并及处理冲突交给外部 Agent。CoBot 下发任务、记录 Agent 报告的工作位置/版本/证据、协调测试与审查、路由用户决定；不内置 Git 管理器，不把批准合并与执行合并混为一件事。

**待讨论。** 场景模板如何提示隔离、谁执行授权后的合并、位置如何回报、清理时机及远程 PR 是否需要。测试和审查引用同一候选版本，不能把批准某个版本扩展成对后续变动的自动批准。用户授权后 Agent 可以合并，未经授权不能自行执行。

权限保证依赖外部引擎实际支持的沙箱、审批或工具门禁。仅发送“不要合并”等指令无法保证硬性阻断，不宣称提示词能限制所有 Git 动作。

**验收条件：** 双任务修改不冲突；测试和审查引用同版；用户决定正确传给执行者；结果回写任务；冲突不覆盖已有工作。

## 8. 审批与记录（R06）

**已确认。** 安全审批和协作确认进入统一队列，招募申请也复用审批流程。中断恢复卡使用同样的展示与记录方式，显示在队长会话。卡片只向用户展示，不进入队长或其他成员的模型上下文；客观结果可回写相关任务。

待审批卡在发起 bot 和队长的会话输入框上方共享显示，各入口处理一次即生效。队长队列覆盖全团队；成员队列只包含自己发起的卡，中断恢复卡仅在队长队列。

**交互规则：**

- 一次一张，卡片右上角显示当前位置 / 尚待处理总数，例如 `‹ 1 / 2 ›`，可上一个、下一个；翻页不代表批准，不自动轮播。
- 处理完当前卡即移除，更新数量并显示相邻待处理卡；全部处理完后队列区域消失。
- 没有“待你处理 N”标题、审批记录按钮、“还有一张……”说明；输入框上方永远不重复“等你审批”。等待状态与跨会话待办在团队列表表达。
- 右侧页面仍名为“审批”，只展示已处理记录；没有待处理分类、操作按钮或待审批数量徽标。
- 历史保留类型、发起者、申请时间、动作、真实理由、当时全部选项及所选项、处理入口和处理时间；成员可看到由队长处理的自身请求历史。
- 卡片处理后不留在用户会话消息流里。

| 卡片 | 当前草案选项 | 状态说明 |
| --- | --- | --- |
| 安全审批 | 允许一次、总是允许（这个 bot）、拒绝 | 展示方向已确认；常驻授权匹配范围、撤销与引擎映射待定 |
| 协作确认 | 继续、附一句指示再继续、停止当前协作 | 继续与停止方向已确认；具体措辞和补充指示机制待讨论 |
| 中断恢复 | 继续、重跑当前工作、放弃 | 延用此前恢复建议；具体恢复能力待验证 |
| 招募申请 | 批准或拒绝引入指定角色 | 用户批准是硬要求；卡片细节待讨论 |

等待审批时不默认拒绝，相关工作等待用户；超时自动拒绝仍是建议。低风险自动放行与高风险请求审批的分级细则待讨论。自动授权日志如何进入用户历史，应与人工处理记录区分，不能伪装成用户批准。

**验收条件：** 从队长处理后成员卡片同步消失；并发点击只产生一次结果；处理前不会进入右侧历史；翻页不执行动作；保留准确的原选项与选择。

## 9. 内部轮次控制（R07）

**已确认方向。** 用户消息或一次批准开启协作链；一个 bot 被其他 bot 的消息或交接唤醒记一轮，一轮内工具调用不计。用户插话或批准继续后重新计数。默认上限 6，可调大；到上限请求用户决定是否继续。

上限前有风险区，由小模型判断下一步是否需要用户确认。历史建议为最后 20%，例如上限 10 时第 8 轮起；具体取整、计数对象与小模型来源待技术设计。小模型不能替用户批准高风险操作。

**界面规则。** 轮数、上限与风险区不在日常界面和新建团队中展示。内部限制、持久化与审计仍保留；可配置入口尚未决定。确认卡围绕下一步和真实事项呈现，具体文案继续讨论，不能为隐藏计数虚构安全风险。

**验收条件：** 重启不能绕过计数；同一唤醒重放不会重复计轮；上限处不会未经用户批准继续启动协作；日常界面无轮数提示。

## 10. 记忆（R08）

**已确认。** 按 bot 独立、按团队隔离；只保存工作方法与偏好，用户可查看与删除。入口在右侧，队长看自己的记忆，成员看当前成员的记忆。

**建议：** 每轮结束提炼要点，下一轮按相关性带入。结构、检索方式、冲突事实处理和删除后避免重新提炼同一事实的策略待定。G18 的“团队共享事实”尚未单独采纳，不能据此做跨 bot 自动共享记忆。

**验收条件：** 切换成员不会看到上一人的记忆；跨团队检索被拒绝；删除后不再被当前检索带入；任务证据不依赖记忆召回。

## 11. 成本与预算（R09）

**已确认方向。** CoBot 管理成本，轮次与预算状态需要持久化。当前功能清单提出 token 账本、bot 与团队两级预算熔断：拒绝启动超额新轮，正在运行的轮次允许结束。

**待讨论。** 登录方式采用现有 Codex 订阅登录还是 API key；预算用 token 还是金额；预算默认值与配置入口；小模型用哪个账号/引擎；未知用量如何计账。token 账本及熔断细则属于当前方案建议，不代表已选定计费方式。

用量页面以后独立做；首页右侧不重复展示统计，新建团队不要求填写预算。不能把 token 数直接解释为订阅剩余额度或已产生费用。

**验收条件（待预算方案确认）：** 重复事件不重复记账，bot 与团队统计一致；超额不能启动新轮；缺失的用量标为未知而非零。

## 12. 引擎、运行与凭据（R10）

**已确认方向，基础接入已有本机验证。** V1 接 Codex app-server，让 Codex 处理单次工作的模型与工具循环，CoBot 管理身份、记忆、任务、协作、审批、成本和恢复。保留引擎无关协议，以后可接自带工具循环的完整 Agent；仅模型 API 的执行循环不纳入当前核心。

Go 本机核心由桌面客户端与本机 Web 复用，建议不为 Web 另造业务后端。引擎进程布局、跨平台分发和最小版本尚未确定。凭据只保留一份，不复制到团队目录、任务分支、文档或原型；多 bot 共享登录时的并发与刷新行为需要验证。

**验证状态。** 本机 CLI 0.161.0 在临时优先 MXC 的配置下，原生命令/文件读写、多 bot 基础运行、正常 resume、结构化 MCP 调用和原生审批已有通过证据，范围见[接入基线](接入基线.md)。MCP 业务送达仍是模拟；真实投递/唤醒、队列、任务、持久化、登录刷新与故障恢复随实现验证。尚未证明完整产品流程或所有平台/配置，不要求先完成整套崩溃方案。

**验收条件：** 无机器专属路径；协作不解析模型文本；服务退出、恢复和审批行为可区分成功、失败、被打断和未知；凭据不会进入项目。

## 13. 持久化与崩溃恢复（R11）

**已确认。** 消息、交接、审批、运行状态、协作计数和用量要落数据库。先记状态再执行。CoBot 崩溃后不能丢失未处理消息，也不能假定已发送给 Codex 的工作必然停止。

**已确认方向，恢复细则待验证。** 重启导入落盘事件，与外部引擎线程记录及资源/成果证据对账（编程时可包含分支改动）；能确认完成的补记结果，未送出的续送，已发送但不确定的标“失联待核对”。中断轮次不自动重跑，用户选择继续、重跑或放弃。记录无法证明结局时标“未知”。

失效审批需要区分用户决定与引擎执行结果。“命令未执行”必须有执行状态支持；仅凭宿主退出或轮次消失不能作此判断。请求作废、自动拒绝等系统终止状态是否展示在“审批”页，仍需与仅收已处理记录的规则一起讨论。

**验收条件：** 在消息写入、发送应答、审批响应及工具完成等边界崩溃后，都能归类为已知结果或明确未知；重复恢复不重复产生工作；恢复卡附任务、已知成果/位置与变更；分支只在编程场景适用。正常保存和重启是首版要求，完整崩溃注入与离线降级随实现验证，不作为所有开发工作的前置门槛。

## 14. 离线降级与 hook 事件（R12）

**方向已确认，能力待验证。** 希望 CoBot 不在时 Codex 可以继续思考与允许的读取，但暂停修改、命令和协作。命令类型 hook 本地读取租约并明确拒绝不允许的动作；事件实时转发失败后落盘，CoBot 重启导入。

hook 未受信任、脚本错误、超时、工具覆盖不足、已有命令继续运行都是风险。不能仅凭设计声称已经实现“不停但降级”的硬保证。若目标版本无法满足，需回到用户讨论，不能静默退化为无限制运行。五项原验证前提和扩展检查见[首版开发方案](首版开发方案.md)与参考文档（仅本机归档，非必读）。

**验收条件：** 在确定的工具覆盖内测试离线阻断和事件落盘；未验证路径不能标为安全；重启导入幂等；脚本异常及已经运行的子命令有明确结果与处置。

## 16. 端到端流程与总体验收（R17）

1. 创建团队，选择工作目录，可勾选初始成员；创建目录内 `.cobot` 交互资源，所有成员获得目录信息，重复及嵌套绑定被拒绝。
2. 用户向队长提需求；队长建立任务、完成标准和依赖，指派唯一负责人。
3. 外部 Agent 按编程场景准备独立分支和任务 worktree，回报实际工作位置；需要接口对齐时调用结构化消息工具，结论写回任务。
4. 需要批准的动作在会话卡片等待用户；用户处理后双方卡片消失，右侧记录结果，动作才按批准范围继续。
5. 开发提交证据，测试与审查针对待合并版本验证；阻塞有明确问题和责任人。
6. 用户决定是否合并，由获授权的外部 Agent 执行并回报；版本变化或冲突不能静默忽略。交付后的 CoBot 能继续下一项开发任务。
7. 验证开发/生产配置和数据隔离，开发测试只运行开发服务即可经 Web 操作；检查正常保存和重启。随实现注入崩溃，区分续送、已完成、中断和未知，不自动重跑未确定工作。

这是未来产品验收路径，不是本次已执行的测试。通过标准为上述闭环能用于开发 CoBot 本身，且权限、隔离、审批和恢复规则都成立。演示聊天流畅或单个模型能编程不足以代替这个验收。
