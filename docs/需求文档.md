# CoBot 需求文档（持续讨论草案）

- 版本：0.1，2026-10-14；覆盖第一至十一轮讨论。
- 状态：当前已知内容的整理，不是最终版，不冻结范围。
- 依据：[决策日志](决策日志.md)、[界面布局](界面布局.md)和工作站原 V1 功能清单；来源与迁移映射见[整理与迁移记录](整理与迁移记录.md)。
- 本文的验收条件描述未来实现应如何检查；本次文档整理不表示这些产品能力已实现。

## 1. 定位、目标与边界

**已确认。** 在本机把多个 AI 编码智能体组织成团队，为同一个软件开发目标分工、沟通、验证和审查。用户主要向队长提需求，也可以直接与任何成员沟通。团队以工作目录为边界，不设置额外的“项目”层。

开源，前期先自用；实现不绑定作者的机器路径或专属配置。V1 只接 Codex，先用浏览器访问本地网页，保留后台服务与界面分层。以后预留 Claude Code 与模型厂商 API，桌面壳放在 V1 之后。

V1 的目标验收场景是**用 CoBot 开发 CoBot 自己**：队长拆任务，成员在独立工作区开发，测试验证，审查把关，用户决定高风险动作与合并。

**V1 不做：** 群聊；定时任务、事件触发、后台常驻和开机自启；跨团队聊天、记忆与成员共享；服务器部署、多机协同、手机访问；Claude Code/API 引擎的实际接入；办公、学习、创作等非开发角色；独立成果库；界面编辑角色文件。用量独立页面留到以后，不提前在导航摆出尚未设计的功能入口。

不做无人值守能力的含义是：CoBot 运行期间，已启动任务可以在用户没有持续盯着页面时推进；遇到需要输入或审批的步骤仍停下等待用户。

## 2. 状态标注与核心对象

| 标注 | 解释 |

| 已确认 | 用户明确拍板的规则；如果实现不可行，应回到讨论，而非静默换方案 |

一个条目的状态不自动覆盖其下标为建议的细则。编号 R01～R17 用于连接技术方案与验收条件，后续尽量保持编号稳定。

| 对象 | 定义 |
| --- | --- |
| 团队 | 一个队长和若干成员，绑定一个本地工作目录 |
| 队长 | 创建团队时产生，拆任务、指派负责人、协调交接，可申请招募成员 |

| 目录标记 | `.cobot` 目录；只是本机绑定标记，数据库才是绑定的事实来源 |

## 3. 团队与目录（R01）

**已确认。** 用户创建团队时填写名字、选择工作目录，同时产生队长，可以勾选初始成员，之后随时引入更多成员。日常新建界面只有名称、目录与成员选择，不要求填写轮数、风险区或 token 预算，不解释 `.cobot` 与 Git 排除配置。

一个目录只能绑定一个团队。数据库登记规范化路径，工作目录内写 `.cobot` 标记；删除标记不会解除绑定或允许产生第二个队长。

**已确认的边界处理：**

| 情况 | 期望行为 |
| --- | --- |
| 同目录不同大小写、斜杠或链接写法 | 解析真实位置后视为同一目录，Windows 比较忽略大小写 |
| 新目录包含或位于已绑定目录内 | 禁止嵌套绑定，说明涉及的团队 |
| 数据库有绑定，标记被删 | 拒绝重复创建，可按数据库恢复标记 |
| 标记存在但本实例数据库没有对应团队 | 不自动接管，用户选择接管为新团队或取消 |
| 标记编号对应另一个仍存在的目录 | 视为复制目录，只能按新团队接管并重写标记 |
| 已绑定目录不见了 | 标为目录丢失，不启动成员；由用户重新指定位置 |
| 用户指定新位置，标记携带同一个团队编号 | 按搬家更新绑定，仍要检查重复与嵌套 |

标记写入 `.git/info/exclude`，不修改工作仓库的共享 `.gitignore`。团队列表、归档、删除属于当前功能清单；删除团队解除绑定与标记，不删除代码。**建议：** 目录应是 Git 仓库，非仓库时提示用户初始化；删除或归档有进行中任务时的处理次序仍待讨论。

**验收条件：** 删除 `.cobot` 后再次创建仍失败；同路径别名与嵌套被识别；目录丢失不会启动任务；删除团队不会删除代码。

## 4. 队长、成员与权限（R02）

**已确认。** V1 的五种内置成员角色是产品经理、前端开发、后端开发、测试工程师、代码审查。队长单独承担协调职责，不算这五种专业角色之一。

| 动作 | 用户 | 队长 | 成员 |
| --- | --- | --- | --- |
| 引入内置角色 | 可直接操作 | 可申请，每次必须获用户批准 | 无此权限 |
| 查看角色库 | 可供选择 | 完整内置库 | 只知道本团队已存在的成员 |
| 创建、拆分与指派任务 | 可直接管理任务板 | 可执行 | 可提议，不可自行建任务或指派 |
| 更新任务与提交证据 | 全部任务 | 协调与管理 | 自己负责的任务 |
| 转交自己的任务 | 可管理 | 可协调 | 可发起，对方接受后生效 |
| 批准高风险动作 | 可 | 不可代批 | 不可代批 |
| 合并任务分支 | 决定是否合并 | 不可自行合并 | 不可自行合并 |

团队名单变化时，在各 bot 下一轮开始前带入最新名单，不额外唤醒空闲成员。用户可移除成员；**建议：** 移除前先转交任务。成员上限默认 6 是历史建议，是否包含队长尚需澄清。角色文件可由用户编辑，界面编辑留到以后，这是实现建议而非已冻结格式。

**验收条件：** 队长招募未批准不产生可运行成员；用户直接引入无需重复审批；其他成员下一轮拿到新名单；成员不能越权指派或批准合并。

## 5. 对话、沟通与唤醒（R03）

**已确认。** 用户可与队长或任意成员直接对话；成员之间、成员与队长之间可双向沟通，用户可查看全过程。不同团队间不可聊天、发消息或共享成员。

用户会话放在中间区域；bot 间沟通称“协作记录”，放在当前 bot 的右侧工作面板。当前界面草案采用只读查看，想插话就给对应 bot 发消息。V1 不做群聊，不沿用早期的群人数、@ 路由规则。

协作动作由 CoBot 的结构化工具完成：发消息、交接任务、汇报完成、向用户提问。消息先存入数据库，再主动投递并唤醒目标；目标忙时排到当前轮结束后，重启续送未完成投递，按编号去重。不能用回复中的特殊代码块作为通信协议。

**建议：** 把发送与运行状态分开；请求返回已收下、已送达、重复、对象不存在、无权限或不可用等客观状态，具体枚举未冻结。用户在工作中追加消息如何排队、打断或引导，仍待讨论。

**验收条件：** 发给别的团队被服务端拒绝；目标忙时消息不丢；已投递消息重放不重复启动同一工作；协作结论可回写任务。

## 6. 任务与交接（R04）

**已确认。** 任务有唯一负责人、描述、完成标准、证据、关联分支和父任务。聊天用于讨论，任务板记录进展和结论，记忆不替代任务资料。

**建议的状态：** 待办、进行中、待审查、完成；阻塞必须说明谁需要回答什么。需要输入是否是独立状态、还是任务标记，待讨论。完成时附测试结果、代码变更、审查结论等与任务相符的证据。

成员转交自己任务，对方接受后生效，任务板留痕并通知队长；接受前原负责人保持责任。用户可直接操作任务板。代码实现、测试、审查的任务依赖应明确表达。

**验收条件：** 交接中不会出现零个或两个负责人；对话约定写回任务；不能仅凭“已完成”的聊天消息认定验收通过。

## 7. 编码隔离、测试、审查与合并（R05）

**已确认方向。** 并行编码任务使用独立分支与 Git worktree，避免多人同时改同一工作区；完成后经审查成员把关，由用户批准合并。队长和成员不能自行合并。

**建议：** CoBot 执行用户批准的合并，有冲突退回开发成员处理。分支基线、worktree 路径、清理时机、测试与审查使用哪个工作区以及是否创建远程 PR，均待讨论。不得把“批准某个版本”扩展成对后来变动的自动批准。

**验收条件：** 两个开发任务改同名文件时工作区仍独立；审查与测试针对同一待合并版本；无用户批准不合并；冲突不覆盖已有工作。

## 8. 审批与记录（R06）

**已确认。** 安全审批和协作确认进入统一队列，招募申请也复用审批流程。中断恢复卡使用同样的展示与记录方式，显示在队长会话。卡片只向用户展示，不进入队长或其他成员的模型上下文；客观结果可回写相关任务。

待审批卡在发起 bot 和队长的会话输入框上方共享显示，各入口处理一次即生效。队长队列覆盖全团队；成员队列只包含自己发起的卡，中断恢复卡仅在队长队列。

**第十一轮交互规则：**

- 一次一张，卡片右上角显示当前位置 / 尚待处理总数，例如 `‹ 1 / 2 ›`，可上一个、下一个；翻页不代表批准，不自动轮播。
- 处理完当前卡即移除，更新数量并显示相邻待处理卡；全部处理完后队列区域消失。
- 没有“待你处理 N”标题、审批记录按钮、“还有一张……”说明；输入框上方永远不重复“等你审批”。等待状态与跨会话待办在团队列表表达。
- 右侧页面仍名为“审批”，只展示已处理记录；没有待处理分类、操作按钮或待审批数量徽标。
- 历史保留类型、发起者、申请时间、动作、真实理由、当时全部选项及所选项、处理入口和处理时间；成员可看到由队长处理的自身请求历史。
- 卡片处理后不留在用户会话消息流里。

| 卡片 | 当前草案选项 | 状态说明 |
| --- | --- | --- |
| 安全审批 | 允许一次、总是允许（这个 bot）、拒绝 | 展示方向已确认；常驻授权匹配范围、撤销与引擎映射待定 |
| 协作确认 | 继续、附一句指示再继续、停止当前协作 | 继续与停止方向已确认；具体措辞和补充指示机制待讨论 |
| 中断恢复 | 继续、重跑当前工作、放弃 | 延用此前恢复建议；具体恢复能力待验证 |
| 招募申请 | 批准或拒绝引入指定角色 | 用户批准是硬要求；卡片细节待讨论 |

等待审批时不默认拒绝，相关工作等待用户；超时自动拒绝仍是建议。低风险自动放行与高风险请求审批的分级细则待讨论。自动授权日志如何进入用户历史，应与人工处理记录区分，不能伪装成用户批准。

**验收条件：** 从队长处理后成员卡片同步消失；并发点击只产生一次结果；处理前不会进入右侧历史；翻页不执行动作；保留准确的原选项与选择。

## 9. 内部轮次控制（R07）

**已确认方向。** 用户消息或一次批准开启协作链；一个 bot 被其他 bot 的消息或交接唤醒记一轮，一轮内工具调用不计。用户插话或批准继续后重新计数。默认上限 6，可调大；到上限请求用户决定是否继续。

上限前有风险区，由小模型判断下一步是否需要用户确认。历史建议为最后 20%，例如上限 10 时第 8 轮起；具体取整、计数对象与小模型来源待技术设计。小模型不能替用户批准高风险操作。

**第十轮补充。** 轮数、上限与风险区不在日常界面和新建团队中展示。内部限制、持久化与审计仍保留；可配置入口尚未决定。用户希望减少机械暂停的感觉，确认卡围绕下一步和真实事项呈现。曾讨论“伪装安全风险”，未作为已确认规则迁入；具体文案继续讨论，不能仅为隐藏计数虚构风险。

**验收条件：** 重启不能绕过计数；同一唤醒重放不会重复计轮；上限处不会未经用户批准继续启动协作；日常界面无轮数提示。

## 10. 记忆（R08）

**已确认。** 按 bot 独立、按团队隔离；只保存工作方法与偏好，用户可查看与删除。入口在右侧，队长看自己的记忆，成员看当前成员的记忆。

**建议：** 每轮结束提炼要点，下一轮按相关性带入。结构、检索方式、冲突事实处理和删除后避免重新提炼同一事实的策略待定。G18 的“团队共享事实”尚未单独采纳，不能据此做跨 bot 自动共享记忆。

**验收条件：** 切换成员不会看到上一人的记忆；跨团队检索被拒绝；删除后不再被当前检索带入；任务证据不依赖记忆召回。

## 11. 成本与预算（R09）

**已确认方向。** CoBot 管理成本，轮次与预算状态需要持久化。当前功能清单提出 token 账本、bot 与团队两级预算熔断：拒绝启动超额新轮，正在运行的轮次允许结束。

**待讨论。** 登录方式采用现有 Codex 订阅登录还是 API key；预算用 token 还是金额；预算默认值与配置入口；小模型用哪个账号/引擎；未知用量如何计账。token 账本及熔断细则属于当前方案建议，不代表已选定计费方式。

用量页面以后独立做；首页右侧不重复展示统计，新建团队不要求填写预算。不能把 token 数直接解释为订阅剩余额度或已产生费用。

**验收条件（待预算方案确认）：** 重复事件不重复记账，bot 与团队统计一致；超额不能启动新轮；缺失的用量标为未知而非零。

## 12. 引擎、运行与凭据（R10）

**已确认方向，待技术验证。** V1 接 Codex app-server，让 Codex 处理单次工作的模型与工具循环，CoBot 管理身份、记忆、任务、协作、审批、成本和恢复。保留引擎无关协议，以后可接自带工具循环的 CLI 或仅提供模型的 API。

仅本机服务与本地网页。引擎进程布局、跨平台分发和最小版本尚未确定。凭据只保留一份，不复制到团队目录、任务分支、文档或原型；多 bot 共享登录时的并发与刷新行为需要验证。

**验收条件：** 无机器专属路径；协作不解析模型文本；服务退出、恢复和审批行为可区分成功、失败、被打断和未知；凭据不会进入项目。

## 13. 持久化与崩溃恢复（R11）

**已确认。** 消息、交接、审批、运行状态、协作计数和用量要落数据库。先记状态再执行。CoBot 崩溃后不能丢失未处理消息，也不能假定已发送给 Codex 的工作必然停止。

**已确认方向，恢复细则待验证。** 重启导入落盘事件，与 Codex 线程记录、任务分支改动对账；能确认完成的补记结果，未送出的续送，已发送但不确定的标“失联待核对”。中断轮次不自动重跑，用户选择继续、重跑或放弃。记录无法证明结局时标“未知”。

失效审批需要区分用户决定与引擎执行结果。原建议“轮次消失就标命令未执行”证据不足：必须有执行状态支持，不能只因宿主退出就如此断言。请求作废、自动拒绝等系统终止状态是否展示在“审批”页，仍需与仅收已处理记录的规则一起讨论。

**验收条件：** 在消息写入、发送应答、审批响应及工具完成等边界崩溃后，都能归类为已知结果或明确未知；重复恢复不重复产生工作；恢复卡附关联任务、分支与已有改动。

## 14. 离线降级与 hook 事件（R12）

**方向已确认，能力待验证。** 希望 CoBot 不在时 Codex 可以继续思考与允许的读取，但暂停修改、命令和协作。命令类型 hook 本地读取租约并明确拒绝不允许的动作；事件实时转发失败后落盘，CoBot 重启导入。

hook 未受信任、脚本错误、超时、工具覆盖不足、已有命令继续运行都是风险。不能仅凭设计声称已经实现“不停但降级”的硬保证。若目标版本无法满足，需回到用户讨论，不能静默退化为无限制运行。五项原验证前提和扩展检查见[技术方案](技术方案.md)与[参考文档](参考/Codex-hook与崩溃降级.md)。

**验收条件：** 在确定的工具覆盖内测试离线阻断和事件落盘；未验证路径不能标为安全；重启导入幂等；脚本异常及已经运行的子命令有明确结果与处置。

## 16. 端到端流程与总体验收（R17）

1. 创建团队并选择目录、成员；重复与嵌套绑定被拒绝。
2. 用户向队长提需求；队长建立任务、完成标准和依赖，指派唯一负责人。
3. 开发成员分别进入任务 worktree；需要接口对齐时调用结构化消息工具，结论写回任务。
4. 需要批准的动作在会话卡片等待用户；用户处理后双方卡片消失，右侧记录结果，动作才按批准范围继续。
5. 开发提交证据，测试与审查针对待合并版本验证；阻塞有明确问题和责任人。
6. 用户决定是否合并；合并未批准、证据版本变化或发生冲突时不能静默合并。
7. 人为注入一次宿主崩溃，重启区分续送、已完成、中断和未知，不自动重跑未确定工作。

这是未来产品验收路径，不是本次已执行的测试。通过标准为上述闭环能用于开发 CoBot 本身，且权限、隔离、审批和恢复规则都成立。演示聊天流畅或单个模型能编程不足以代替这个验收。
