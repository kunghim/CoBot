## 2. 首版 Web 需要先修复的问题（P1）

### R01 登录流程丢弃必要信息，账号投影与真实协议不符

- 位置：`internal/engine/codex/server.go:290`、`:298`；`internal/app/engine_status.go:121`；`internal/api/http/handlers_engine.go:28`；`frontend/src/features/settings/SettingsPage.tsx`。
- 证据：login/start 的响应没有解码，HTTP 仅返回 `loginStarted:true`；前端没有得到或打开 `authUrl`。取消只发送 `{}`，真实 Codex 返回 `Invalid request: missing field loginId`；产品取消接口实际返回 503。
- 账号解析只读 `auth.mode`、顶层 `mode/loggedIn`，实际 account/read 使用 `account.type`。本机生成协议及原验证均可佐证；本轮真实空账号只证明未登录，没有冒充已登录测试。
- 影响：正常独立官方登录无法通过 Web 完成，即使登录成功也不能准确投影。
- 修复验收：保存并隔离管理待登录 ID，向用户提供正确官方授权入口，取消指定登录；解析实际账号联合类型。真实完成登录/取消/登出/重新登录，不能靠虚构响应通过。

### R02 真实可用模型被错误转换为空列表

- 位置：`internal/app/engine_status.go:237`，`sanitizeModels` 只读取 `models`。
- 复现：同版本真实 Codex 在隔离环境返回 `{data:[8项],nextCursor:...}`；产品 `/api/v1/models` 返回 `{models:[]}`；浏览器默认/评估模型选择均无真实选项。
- 修复验收：按实际协议读取与转换，正确处理列表游标；用真实返回形状做契约测试，并在浏览器选择真实模型保存生效。

### R03 中断请求漏传 turnId

- 位置：`internal/engine/codex/server.go:262`；调用涉及用户停止、链停止、服务退出。
- 复现：代码只发送 `threadId`；真实 Codex 直接返回 `Invalid request: missing field turnId`。fake engine 宽松接受了错误请求，所以现有中断测试未发现。
- 影响：不能依赖当前接口正常停止目标执行；正常服务退出的中断步骤同样受影响。
- 修复验收：传入真实当前 turn 身份，处理完成与停止并发；真实多成员/多团队执行中只停止目标，退出时有界收尾。

### R04 MCP 工具缺少可供模型使用的参数契约

- 位置：`internal/collaboration/bridge.go:55`、`:107`。
- 证据：19 个工具全部注册为 `{"type":"object"}`；描述未列参数，模型无法从 tools/list 得知 `targetBotId`、`acceptanceCriteria`、`expectedRevision` 等字段。测试直接构造合法参数，绕过了这个使用问题。
- 影响：协作依赖模型猜测输入，不能作为可靠的多 Agent 产品能力交付。
- 修复验收：逐工具提供真实 properties/required/枚举/描述，身份不作为模型可指定字段；检查 tools/list，并让真实模型完成任务创建、沟通、证据提交及提问。

### R05 既有 Bot 的协作凭据到期后不续期

- 位置：`internal/auth/bottoken.go:59`；`internal/app/scheduler.go:485`、`:509`、`:568`。
- 动态证据：把同一生产路径 TTL 缩短至 120ms；首轮签发 1 个令牌，第二轮正常启动时有效令牌为 0。默认生产 TTL 为两小时。
- 同源缺口：核心重启会清空内存令牌，但成功 resume 的分支不发新令牌、不更新桥配置。真实 Codex 恢复时旧 endpoint/配置的具体保留行为本轮未测，不能将此推断写成已实测。
- 修复验收：明确令牌轮换和桥重配生命周期；覆盖持续使用跨 TTL，以及正常重启后同一 Bot 继续真实 MCP 工作。

### R06 已取消任务仍会启动执行

- 位置：`internal/app/tasks.go:375`；`internal/app/scheduler.go:195`。
- 复现：成员忙碌 → 为其创建任务 → 取消任务 → 原轮结束。任务投递仍为 queued，随后实际启动第二个 turn，输入同时含 `状态：cancelled` 和“你被指派了任务”。两个独立方向均复现。
- 修复验收：取消任务与取消相关未送投递同事务；领取前再次核验任务状态/负责人。已开始执行如何处理应如实表达，不能把取消状态当成已撤回。

### R07 未回答问题未阻止相关任务自动推进

- 位置：`internal/app/questions.go:59`；`internal/app/engine_events.go:163`、`:180`；调度领取路径。
- 复现：成员执行任务时 ask_user → 队长发送与同一任务有关的自动协作消息 → 当前 turn 结束。Question 仍 open，Bot 却进入 working，第二轮已执行。
- 边界：用户主动另发一条消息可以有独立语义，不因这个行为本身判错。正式缺陷由“同任务自动派发未等待答案”的反例证明。
- 修复验收：持久关联等待事项与相关任务，阻止相关自动派发；用户回答后原子落消息与投递，再恢复对应工作。成员状态准确显示需要输入。

### R08 启动回执会覆盖已经结束的执行事实

- 位置：`internal/app/scheduler.go:321`；`internal/store/sqlite/queries_conversations.go:269`。
- 复现：fake 在 StartTurn 返回前发送 completed；完成回调已落库后，启动返回路径仍无条件写 running，数据库最终 `status=running` 且 `endedAt` 已填。
- 影响：产生永久活动 Run，后续消息无法派发；抢先到达的 waiting_approval 也存在被覆盖的同类窗口。
- 修复验收：用受约束状态迁移处理回执，不能覆盖更晚事实；补“响应先于通知/通知先于响应/中断并发”反例。

### R09 恢复操作没有确认旧执行结束就解除锁定

- 位置：`internal/app/recovery.go:190`、`:218`、`:237`。
- 确定事实：仅依据 RunUnknown 写 interrupted；rerun 直接将旧投递改 queued，没有旧执行结束或受管终止的证明。注释假定旧工作随进程死亡，与崩溃后执行可能继续的产品规则矛盾。
- 动态边界：在应用层模拟重启对账，保留尚未发结束事件的 fake turn，选择 rerun 后启动第二个 turn。**这不是一次真实 Windows 核心崩溃/孤儿进程/双重文件写入试验**。
- 修复验收：旧执行终结得到确认前保持锁定；能力不能证明时禁用相应动作并解释。使用受控测试验证终止/未知两种路径，而非仅改数据库状态。

### R10 合并批准后没有结果反馈，协作闭环中断

- 位置：`internal/app/approvals.go:137`；`internal/app/collaboration.go` 的 SubmitMergeRequest。
- 证据：request_merge 返回 waiting；决定 merge 时走通用无引擎响应分支，记 expired/not_engine_bound，没有通知消息、Delivery 或 Wake，也没有供 Bot 查询决定的工具或上下文。
- 影响：申请 Bot 无法结构化获知批准/拒绝，不能按批准的候选继续外部交付。招募拒绝的结果反馈也应一并检查。
- 修复验收：决定及候选身份持久化，可靠投递给原申请者；重复处理不能重复授权或执行。CoBot 仍不自行执行 Git。

### R11 合并候选与证据版本没有一致性校验

- 位置：`internal/app/collaboration.go:242`、`:264`；审批决定路径无 merge 专门复核。
- 复现条件：提交属于任务的 SHA-A 证据，却申请 SHA-B；当前仅验证 evidence ID 属于任务，不比较 CandidateRef/TestResult/ReviewResult。决定时也不检查任务/候选/证据版本变化。
- 影响：用户可在不相符的测试/审查证据下批准另一候选。M5 已承认“候选重绑校验未实现”，不能降格为测试缺口。
- 修复验收：请求绑定不可混淆的候选、目标与相符证据版本，处理时复核；变化后新确认或拒绝。不得宣称这等价于拦截任意间接 Git 命令。

### R12 目录改绑后继续复用旧 cwd 的进程与 thread

- 位置：`internal/app/web_surface.go:211`；`internal/app/scheduler.go:430`、`:487`；`internal/engine/codex/server.go:234`。
- 静态证据：改绑只更新库与标记；EnsureTeamServer 不比较 cwd，ResumeThread 只传 threadId；没有替换现有 runtime，也未先排除活动/未知执行。
- 影响：团队从 A 改绑 B 后，模型上下文声称 B，实际执行仍可能位于 A；这涉及操作目标正确性。
- 修复验收：先约束活动/未知执行，更新进程与会话边界；真实在新目录生成产物，并确认旧目录未被新轮修改。API 修好后还需补 Web 入口，见 R18。

### R13 写请求幂等存在两种实际重复副作用

- HTTP：`internal/api/http/handlers_teams.go:81` 丢弃 requestId；`internal/app/teams.go:325` 每次创建新成员。完全相同请求连续两次均返回 201、不同 Bot ID。创建任务同样未落实 requestId 唯一性。
- MCP：`internal/collaboration/dispatch.go:138` 先执行业务，再另事务存幂等结果。barrier 让同身份/同 key/同参数同时 miss，两个 ask_user 返回不同 questionId，库中生成两个问题。
- 影响：网络重试或重叠请求会多建资源；M5 承认的窗口并非仅参数校验不严格。
- 修复验收：幂等占位/业务变更/结果应有原子性，重试返回同一事实，不同参数冲突；覆盖串行、并行、响应丢失及记账失败。

### R14 开发服务授权入口没有注册

- 位置：`frontend/vite.config.ts:32`；`scripts/dev.ps1`、`scripts/dev.sh`。
- 复现：真实本地 Vite，注入非密占位 adminSecret 后 POST `/__cobot/dev-link` 返回 404。configureServer 被误放在 server 配置中，而非插件 hook；前端 typecheck 只包含 src，没有发现配置错误。
- 影响：按开发脚本打开干净浏览器不能自动授权，阻碍“用 CoBot 开发 CoBot”的正常开发入口。
- 修复验收：正确注册开发插件，覆盖真实 Vite → Go 代理与授权；另核查 proxy 的 Host/Origin 处理、单实例复用和脚本退出，不以修好单个 404 就认定整个开发脚本通过。

### R25 旧页面 cookie 会阻止有效新链接重新授权

- 位置：`internal/api/http/middleware.go:85`，全局 resolvePrincipal 在 bootstrap 路由之前执行；`:176` 对旧会话直接返回 session_expired。`handleSessionBootstrap` 因而没有机会兑换新秘密。
- 复现：真实独立服务 + Chromium cookie jar，设置代表上次服务遗留的无效 `cobot_session`；携带有效新秘密 POST session/bootstrap 返回 401/session_expired。清 cookie 后使用**同一个**秘密立即返回 200，证明秘密有效、请求此前被中间件挡住。
- 影响：页面会话只在服务内存中，正常重启后浏览器仍留旧 cookie；用户打开新授权链接也无法恢复，需要自行清理站点 cookie。会话过期、同主机其他实例的 cookie 也需检查。该问题阻塞正常重启后继续使用，不是崩溃小概率场景。
- 修复验收：短期秘密兑换不被无效旧页面身份挡住，仍严格核验秘密、Origin 和使用次数；真实浏览器覆盖首次授权、正常服务重启、会话过期、同主机多环境和 SSE 失效后的重新授权。
