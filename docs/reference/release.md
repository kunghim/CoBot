# 自动发布

适用场景：把 `main` 上已决定发布的提交检查、打包并公开发布。实现以 `.github/workflows/release.yml` 为准。

## 触发与版本

- `dev` 晋级到 `main` 后自动触发；普通 PR、`dev` 更新和推标签不会触发发布。
- 自动沿用最近发布版的通道：测试版递增末尾序号，正式版递增补丁号。不会自动从测试版转为正式版或升级大版本。
- Windows MSI 版本从前一发布版的 `release-manifest.json` 独立递增，达到字段上限时进位；打包时仍读取前一 MSI 再核对。
- 第一次发布须手动提供产品与 MSI 版本。已有发布版缺少 manifest 时，也可手动提供两个版本，不猜旧安装版本。
- 已发布的同一提交不重复发版；尚未开始执行的旧 main 运行会让位给更新的 main。已占用标签不会覆盖；存在未完成版本草稿时停止自动分配，先检查该草稿。

## 手动入口

打开 **Actions → release → Run workflow**，选择 `main`：版本留空沿用自动规则；指定产品版本可切换通道或升级大版本，MSI 版本可留空递增。
勾选 `draft_only` 时只生成已校验的草稿；默认会公开发布。手动重新运行旧提交不会回退当前版本。

## 工作流做什么

- 对选定的不可变提交重跑 CI，在 Windows 上构建 Windows x64，在 Apple Silicon 上构建 macOS ARM64。
- 有前一已发布版本时运行合成数据升级检查；不通过则不发布。首次发布没有旧版时跳过该项。
- 检查 MSI 内容与版本、Windows ZIP/MSI 载荷、DMG 内架构与临时签名，校验所有本地产物。
- 上传到临时草稿，核对远端恰好包含 Windows MSI、Windows ZIP、ARM64 DMG、三个校验文件及 `release-manifest.json`，并逐个核对大小和 GitHub 返回的 SHA-256。
- 全部上传校验通过后自动 Publish；测试版标为 prerelease，正式版标为 latest。发布说明包含 GitHub 生成的变更列表、来源、检查链接与实际验收限制。
- Intel 包、server 二进制、原始运行日志与用户数据不作为发布资产。上传失败可能留下草稿，不会公开不完整文件；修复后先检查草稿，不覆盖已有版本。

## 权限与验收边界

只有最后的发布任务拥有仓库内容写权限；运行串行，打包期间若另一发布改变了基线则拒绝继续。签名凭据和 Codex 登录不进入工作流。
自动发布不代表交互安装或真实账号已验收：Windows 包未签名，macOS 只有 ad-hoc 签名，没有 Developer ID 签名和公证。
发现原生安装、首次启动或真实 Codex 问题时，依据同批下载资产记录问题，不能把自动检查通过写成全部场景已通过。
