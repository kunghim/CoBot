## 先要知道的前提

Grok Bot 的调度核心在云端，客户端里看不到「谁发言、何时收尾、何时唤醒」的规则。下面的借鉴来自它的协议设计、状态模型、本机执行与审批代码，以及界面文字。

协议里也**没有 bot 对话轮数上限**，它靠收尾标志、发言截止时间、成员可放弃发言、用量上限和群聊成本提醒来控制失控。cobot 已定的「轮数上限 + 风险区小模型判断 + 协作确认卡」更明确，不需要改方向。

## 建议直接采纳

| 编号 | 借鉴点 | 落到 cobot 哪里 |
| --- | --- | --- |
| G1 | 群里 @ 某个 bot 时只带它没看过的新消息，外加群信息和成员列表 | 群聊路由 |
| G2 | bot 被 @ 后可以明确「放弃发言」；每次被唤醒都记录结局：发言 / 放弃 / 跳过 / 超时 / 取消 / 出错 | 群聊、轮次计数、时间线 |
| G3 | 唤醒、交接、发言请求、新建 bot 都带一次性编号，结果按编号对账，重复投递不重复执行 | 后台服务的消息与任务机制 |
| G4 | 「发私信」工具返回分类结果：已送达、重复、对象不存在、无权限（例如跨团队）、对象不可用 | 协作 MCP 工具 |
| G5 | bot 状态分两半：实时状态（在跑、正在写、正在重试、当前工具与目标、在等什么及开始时间、过期时间）+ 用户侧状态（未读、通知） | bot 状态徽标、队长 的成员视图 |
| G6 | 用户消息先有发送状态，再有运行状态；网络中断时用消息编号事后查询 | 网页界面与后台服务的通信 |
| G7 | 推给网页界面的事件流用「顺序号 + 更新序号 + 游标」，断线重连后补齐新增和修改 | 后台服务的事件推送 |
| G8 | shell 命令先解析成语法树、拆出子命令和重定向；解析失败即拒绝；禁止名单命中不可审批；拒绝理由写给 bot 看，告诉它可以继续做别的 | 安全审批 |
| G9 | 每个被放行的动作记录授权来源（常驻规则还是某次审批）和审批编号，可撤回 | 审批记录 |
| G10 | 一轮的结束方式加「被取代」：用户在 bot 没答完时又发了新消息 | 轮次与任务状态 |
| G20 | 消息先存后送、送到即唤醒：先写数据库，再主动唤醒目标；目标在忙就排队到这一轮结束；重启后续送；按编号去重（第四轮已采纳，并扩展为崩溃恢复要求） | 后台服务的消息机制、崩溃恢复 |

## 建议改造后采纳

| 编号 | 借鉴点 | cobot 的调整 |
| --- | --- | --- |
| G11 | 收尾信号：服务端判断群聊该收尾就通知成员 | 进入轮次风险区时，给参与的 bot 带一句「这段协作正在收尾，请尽快给结论或交给队长」，与小模型判断、协作确认卡并用 |
| G12 | 「这次发言由哪次请求引出」的父子链 | 用来实现轮次计数：同一条链上的唤醒累加，用户插话开启新链 |
| G13 | 用户写「允许规则」和「拦截规则」两组自然语言，模型据此自动审查 | 风险区的小模型判断读同一套规则；卡片标明「已按你的规则自动批准」或「已标记为可能存在危险」 |
| G14 | 审批四档：允许一次 / 拒绝 / 总是允许 / 从不；总是允许分「这个 bot」和「全团队」 | 作用域改为「这个 bot」和「本团队」 |
| G15 | 用户给每类动作设权限上限，bot 申请不能越过 | 放进团队内部配置 |
| G16 | 按命令类型给网络权限：只有依赖安装类命令才放开网络 | 编码 bot 的沙盒策略；Windows 下补 PowerShell 解析 |
| G17 | 每轮结束时整体维护任务清单（本轮消息、是否在等用户、结束方式、完成与失败的工作） | 每轮结束时让 bot 用工具上报任务进展；任务状态加「需要输入」 |
| G18 | 记忆以「一条事实 + 时间」为单位，默认私有，共享须用户勾选 | bot 记忆按事实存；「提升为团队共享知识」须用户确认 |
| G19 | 在场感知：用户离开且没有进行中的工作时停放资源 | 空闲 bot 的 `codex app-server` 进程可以退出，需要时再拉起 |

## 不采纳

- 云端沙盒与 Temporal 工作流、沙盒迁移与升级调度：cobot 只在本机运行。
- Grok Bot 的多用户组织、发布、市场、Slack / Teams / 邮件接入：前期自用。
- 例行任务与事件触发：V1 不做无人值守；「无人查看时暂停例行任务」留作以后做自动化时的参考。
- Grok Bot 的「主 Bot」是用户级的默认助手，不是项目协调者；cobot 的队长 权限模型是自己的设计，无可照搬。
