# 默认工作区、项目与成果保存位置（定向调研）

- 日期：2026-10-14。
- 问题：Muse / Grok Bot 为何可以不让用户先选项目目录？是否默认在应用工作区执行，指定项目或保存位置后再写到该处？
- 状态：事实、推断与 CoBot 建议分别记录；本文不冻结 CoBot 的目录布局。
- 方法：两个子 Agent 分别研究 Grok Bot 安装代码与用户指定的 Muse 官网，主 Agent 复核关键材料。未操作登录态、调用产品账户接口或启动目标应用。

## 1. 先区分位置的用途

| 位置 | 保存或决定什么 |
| --- | --- |
| 应用数据根 | 会话、任务、审批、配置、缓存等应用状态 |
| Agent 执行目录 | 工具的 cwd、相对路径起点和执行上下文 |
| 用户项目/资料 | 用户希望处理的现有资源，可以是代码或普通文件 |
| 成果位置 | Agent 生成文件的位置，或用户下载/另存为的目的位置 |

这些位置可以关联，也可以分开。用户省去项目选择，应用仍需为 Agent 提供执行上下文。下载到本机某目录，也不能直接证明生成过程在该目录发生。

## 2. Muse：官方明确是用户的云端电脑

用户确认目标为 [muse.ai](https://muse.ai/?return_to=%2Fplatform)。当前官网是 Meta 的个人 Agent；搜索结果中该域名的旧视频服务资料不用于本轮结论。

**官方说明。** 每用户拥有持久、隔离的 Linux 云端 VM，客户端连接该 VM。Agent、工作区、文件和工具位于 VM 的运行容器；持久应用状态在运行容器之外的 PostgreSQL 中。上传、生成及使用的文件保存于 VM，用户可以查看、编辑和下载。[官方架构与安全说明](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)，对应“An agent in your own cloud computer”“Muse Secure VM”“Our Policy Around Data”。

**官方说明。** 产品围绕主聊天、旁聊、目标与任务组织体验，拥有文件系统、终端和浏览器，能交付文档、PDF、网页等 Artifacts。[官方设计说明](https://introducing.muse.ai/)

**推断。** 它能从目标和聊天开始工作的一个原因，是平台已经提供了持久执行环境。用户不需要先把一个本机代码项目当成所有工作的入口；未实操登录后的创建表单，不宣称已经验证全部创建选项。

**未知。** 已查官方资料未公开默认 cwd 的准确路径，也未证明可绑定任意本机项目目录、自动写入任意本机位置，或下载界面的具体目录选择规则。不能由“可以下载”推断“可以在本机项目中直接执行”。

### 目前已核实的行为路径

**观察：`.grokbot` 的确在默认数据根代码中。** `main-core.cjs @335545` 附近定义 `SAND_DATA_ROOT`、`.grokbot`、`SAND_USER_DATA_DIR`、`sand-data` 与 `--user-data-dir`。`Me` 在绝对 `SAND_DATA_ROOT` 覆盖不存在、未指定 user-data-dir 且模式为 `sand` 时返回 `homedir()/.grokbot`；指定用户数据目录时取其 `sand-data` 子目录，开发/实验模式另走 `.cursor` 下的相应目录。daemon `@1910813` 附近有同类解析，并将审批、常驻授权及 computer-use 数据放在解析得到的数据根中。

**观察：有模型可见路径别名。** `main-core.cjs` 的相邻 `OZ/Jf` 代码包含 `/home/box/agent-data`、`.grokbot` 和 `.cursor/sand` 等路径识别及映射。模型看到的路径可能经转换，不能直接当成本机实际文件路径。

**观察：本机执行 root 有另一套默认规则。** daemon `@2871795` 的 `rYe(env)` 优先取非空 `SAND_LOCAL_EXEC_ROOT`，其次 `SAND_AGENT_PROJECT_DIR`，否则取 `homedir()`；`@3509151` 的启动调用实际把它传给 `rQe`。`@2873315` 的 `oYe` 用该 root 配置 shell、读文件及列目录。这里证明的是安装代码的默认和覆盖规则，本轮未读取用户实际环境，也不能据此反推云 box 的默认 cwd。

**观察：指定 shell 工作目录有有效性处理。** daemon `@2872367` 的 `XKe` 对显式目录做存在检查，存在则采用，不存在则回退 root 并输出提示；不自动创建该目录。`@2872820` 的 `LE` 包含文件读/列/上传/下载的 root 及符号链接越界拒绝分支。Shell 路径另走 cwd 和下层审批/沙箱处理；不能把文件传输的 root 检查当成所有工具的统一权限保证。

**观察：本机另存为独立选择。** `main-app.cjs @1754888` 附近 `ee` 调用保存对话框，以 OS Downloads 和建议文件名构建默认目标，取消则返回空；随后 `se` 按选定的 `targetPath` 写入从附件分块读取的文件。它证明客户端有“内部附件 → 用户选择本机目的地”的导出流程，尚不能证明全部文件入口都走这一条。

**观察：Bot 文件也是独立业务对象。** `main-app.cjs @2084641` 附近 `I9e` 按 Agent 身份列文件，上传依次计算摘要、申请上传 URL、写入 URL、完成提交；不只操作本机目录。`proto.cjs @934156` 的创建请求使用身份、名字、harness、purpose、origin、language 和 create intent，无必填 repo/workdir。

**观察：执行上下文分别建模。** `proto.cjs @431759` 的 `RequestContextEnv` 包含 workspace_paths、project_folder、artifacts_folder、notes、transcripts、process_working_directory、mounted_agent_stores 等字段；`@432892` 附近的挂载项还有 path、kind、alias 和 read_only。仅字段存在不能证明服务端默认值或实际挂载规则。

**限定推断。** Bot 身份、应用状态、执行资源和用户导出文件可以分开组织。`.grokbot` 支持了用户对“应用自己的数据位置”的猜测；它还不足以证明“所有 Bot 默认 cwd 都是本机 `.grokbot`”或“对话指定本机项目后，所有成果自动写进该项目”。

**未知。** 尚未看到云端工作目录的统一生成器，以及通用 UI/自然语言“指定项目”到持久本机目录绑定的完整实现。本轮不访问云运行环境，不能补出每 Bot/会话的云目录层级。

数据根解析中的 `Me` 调用 `By([], process.env)`；`--user-data-dir` 虽有解析函数，是否由启动入口转写环境仍依入口而定，不能宣称任意位置传该参数必然改变数据根。`main-core.cjs @847239` 有按 packaged/生产 box 条件设置 `SAND_PACKAGED` 的启动代码，当前观察不是只从路径字符串猜测产品模式。

## 4. 对用户假设的逐项判断

| 假设 | 当前结论 |
| --- | --- |
| 通用协作应用可以不强制选择项目目录 | 有支持：Muse 提供云环境，Grok Bot 创建协议不以仓库为前提 |
| Grok Bot 默认所有工作都在本机 `.grokbot` | 不能这样概括：它是数据根，本机执行 root 默认 home，云执行默认值未知 |
| 用户可把成果保存到指定位置 | Grok Bot 桌面另存为有代码支持；Muse 确认可下载，具体选择目录 UI 未核实 |
| 在对话里指定本机项目就自动切换并持久绑定 | 仍未验证；有工具 cwd/上下文字段，不足以证明完整产品流程 |

## 5. 第十五轮 CoBot 候选建议（历史）

以下保留调研时的建议。第十六轮已明确：默认工作区 `~/.cobot`、用户必选团队目录、目录信息全员可见、所选目录内 `.cobot` 保存交互资源且不自动提交。当前需求以 R01 为准；下列“按需指定目录”不作为 CoBot 创建规则。

1. 团队以协作目标和成员组织。创建时可由应用提供默认执行环境，项目/资料位置按需要指定，不把 Git 仓库作为通用入口。
2. CoBot 保存自己的协作数据，并为外部 Agent 准备执行上下文；Git、文档处理等业务操作继续交给外部 Agent。
3. 分别表达“处理哪些资源”和“成果保存到哪里”。用户选了项目，也可能要把报告保存到另一个位置；没有指定成果位置时需明确默认规则。
4. 路径、输出指示与实际权限分别传递。指定保存位置后，仍要确保外部引擎允许对应范围并正确审批。显式目录不可用时报告并请求修正，避免回退到更大的默认范围继续写。
5. 不复制 Muse/Grok Bot 的云架构。CoBot 使用本机核心及本地数据，开发/生产数据隔离；目录名称、按团队/成员划分、交付 UI 与清理策略仍待确定。

对应需求 [R01](../需求文档.md)、技术 [T05](../技术方案.md)。参考产品研究支持通用协作不必以 Git 仓库为入口；CoBot 的目录选择规则由用户另行明确，内部划分和成果交付继续讨论。
