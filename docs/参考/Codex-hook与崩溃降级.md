## Codex hook 能做什么（2026-10-13 历史调研）

共 12 个触发时机：工具执行前、请求权限、工具执行后、上下文压缩前、上下文压缩后、会话开始、会话结束、用户提交、子 agent 开始、子 agent 结束、一轮结束、被打断。和 cobot 关系最大的四个：

| 触发时机 | 能否拦截 | 拿得到的信息或能力 |
| --- | --- | --- |
| 工具执行前 `PreToolUse` | 能。返回 `permissionDecision: "deny"` 并附非空理由，或以退出码 2 退出并在错误输出里写理由。返回「允许」「询问」以及改写参数，目前都不支持 | 工具名、工具参数、会话编号、轮次编号 |
| 请求权限 `PermissionRequest` | 能拒绝 | 工具名、工具参数 |
| 一轮结束 `Stop` | 能阻止结束（要求继续） | 最后一条回复、会话编号、轮次编号、对话记录文件路径 |
| 会话开始 `SessionStart` | 不拦截 | 能注入补充上下文；能区分是新开还是恢复 |

执行方式有两种：跑命令（可以单独给 Windows 写一份命令，可设超时、异步、状态提示），或调用某个 MCP 服务器上的工具（参数用模板从事件里取值）。源码里还声明了 prompt、agent 两种类型，但都是空结构，像是预留。

**最关键的一条：hook 出问题时放行（fail-open）。** 源码里，hook 运行出错、超时、退出码不是 0 也不是 2、输出格式不对、MCP 服务器连不上，都只记为「hook 失败」，工具照常执行。只有 hook 明确返回拒绝才会拦下。

**信任**：hook 必须先被 Codex 信任才会执行，信任按内容哈希记在 `~/.codex/config.toml` 的 `[hooks.state]` 段；没被信任时静默不执行。Orca 的做法是通过 app-server 的 `hooks/list` 让 Codex 自己算出哈希，再用 `config/batchWrite` 写入信任。

**MCP 服务器可以设为「必需」**（配置项 `required`），必需的服务器初始化失败时会报错。从字段名和报错信息看，会话会起不来。

## 方案：Codex 不停，cobot 不在时降级

1. **租约文件**：cobot 每隔几秒写一次本地租约文件，内容包括 cobot 进程编号、心跳时间，以及每个 bot 当前是否放行和原因（正常、被你暂停、预算用完、轮次到上限等）。
2. **工具执行前的命令 hook**：在本地读租约，判定 cobot 不在线（心跳过期或进程不在），或这个 bot 未被放行时，主动返回拒绝，并写明原因和建议，例如「cobot 已离线，暂停修改和命令，请写好进度说明后结束本轮」。判断必须放在 hook 自己身上，不能依赖去连 cobot：否则 cobot 一挂，hook 跟着失败，反而放行。
3. **请求权限的 hook**：cobot 不在线时直接拒绝，不让审批请求干等。
4. **事件转发与降级落盘（用户提出）**：一轮结束、工具执行后、请求权限、被打断、会话开始和结束等事件，都交给同一个命令 hook 脚本处理。cobot 在线时实时发给 cobot；发送失败，或者租约显示 cobot 不在线，就写进约定的落盘目录。cobot 启动后先把落盘目录里的事件按顺序导入数据库，再用 Codex 的线程记录兜底对账。Orca 的 hook 也是这么做的：先发给本机服务，失败就写盘等待重放，总量上限 5 MB、保留 7 天。
5. **MCP 的分工**：协作工具由 cobot 提供，cobot 不在时自然用不了；cobot 的 MCP 服务器设为「必需」，cobot 不在时新会话起不来。MCP 类型的 hook 不能当安全闸门，因为连不上就放行；它也做不了降级落盘，因为连不上时我们自己的代码根本没有机会运行。所以拦截和降级的逻辑都必须写在命令类型的 hook 脚本里。

一个脚本兼顾两件事：遇到「工具执行前」和「请求权限」，先在本地读租约做决定，不依赖网络；所有事件都按「在线就实时发、发不出去就落盘」转发。脚本里任何一步出错，都要落到明确的结果上：拦截类事件给出「拒绝」，其他事件转为落盘，不能以出错退出，否则 Codex 会当成 hook 失败而放行。

## 约定文件（落盘目录）的设计

- **位置**：放在 cobot 的应用数据目录下，按 bot 分子目录；不放在工作目录和任务分支里。路径在启动 Codex 时通过环境变量交给 hook 脚本。
- **一个事件一个文件**：每个事件写成单独的 JSON 文件，先写临时文件再改名。这样多个 bot 同时写也不会内容交错，写到一半崩溃也不会留下半行。文件名带时间和事件编号，方便排序。
- **事件编号**：由会话编号、轮次编号、事件类型和工具调用编号组成。cobot 导入时按编号去重，同一个事件即使实时送过一次、又落盘一次，也不会重复记账。
- **只记元数据**：事件类型、bot、会话与轮次编号、工具名、命令摘要、时间、最后一条回复，不写文件内容。命令里可能带密钥，写入前要对常见密钥格式做脱敏；目录只允许当前用户读取。
- **有上限**：例如总量 5 MB、保留 7 天（参考 Orca）。超出时保留最新的，并在数据库里标记「有事件缺失」，对账时以 Codex 线程记录为准。
- **快速路径**：租约显示 cobot 不在线时直接落盘，不尝试连接；在线时实时发送也只等很短的时间（例如半秒），超时就落盘，避免拖慢每一次工具调用。
- **导入时机**：cobot 启动时全部导入；运行中也定期检查一次，覆盖「cobot 在线但短暂连不上」的情况。导入成功的文件删除或归档。
- **和 Codex 线程记录的关系**：落盘事件是 cobot 自己的主记录，格式由我们定，解析稳定；Codex 线程记录作兜底，补上 hook 没覆盖到的部分，比如 hook 没被信任、脚本崩溃、或者某个工具没触发 hook。

预期效果（待验证，不是已实现保证）：cobot 崩溃时希望不用强行结束 Codex。Codex 还能思考、能读文件，但改不了文件、跑不了命令、发不了消息，会按指令写好进度说明后结束这一轮；cobot 回来后对账续上。

候选附带收益（待工具覆盖与执行语义验证）：同一份租约文件在 cobot 在线时也能把规则落到 Codex 的工具层硬性执行。bot 预算用完、轮次到上限、被你暂停，或者要改的文件不在它的任务目录里，hook 直接拒绝，不只靠提示词约束。

## 前提与风险

- 安全 hook 没被信任就会静默不执行，等于放行。cobot 每次启动都要检查安全 hook 的信任状态，不满足就不启动 bot。
- hook 脚本自己崩溃也会放行，所以脚本要极简，不依赖外部环境。
- hook 拦不住崩溃前已经在跑的命令，这部分仍然要靠进程管理。
- 每次工具调用都要起一个 hook 进程，需要实测在 Windows 上的耗时。

## 放进 app-server 小验证一起测

1. cobot 被强制结束后，app-server 是否随之退出。如果会退出，崩溃场景下 hook 用不上（Codex 已经没了），但它仍保留两个用途：cobot 卡死没退出时的保护，以及在线时硬性执行规则。
2. 能否通过 app-server 为 cobot 管理的 Codex 配置目录写入 hook 信任。
3. 「工具执行前」覆盖哪些工具：shell 命令、改文件、MCP 工具是否都会触发。
4. hook 进程在 Windows 上每次调用的耗时。
5. 必需的 MCP 服务器在会话中途断开时，Codex 怎么表现。
