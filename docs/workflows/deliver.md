# 交付流程

适用：改动做完、准备汇报，或用户要求提交、推送、开 PR。

## 汇报

1. 按 [验证流程](verify.md) 跑完检查。
2. 看一遍最终差异：有没有意外改动、生成文件漂移、私人内容（本机路径、凭据、录制）。
3. 汇报改动后的行为、涉及的文件、实际跑过的验证和结果、没覆盖的范围。到此为止。

## 提交、推送与 PR

- 不主动询问或提议 commit、push、开 PR、合并；用户需要时会直接说。
- 一次授权只覆盖当时点名的那批改动；开始新需求后授权失效。
- 新需求的改动在用户明确验收前，不 push、不开 PR，即使之前授权过。自己跑通测试不算验收。
- 只 `git add <具体路径>`，不用 `add -A`、`add .`、`commit -a`；不擅自 reset、stash、rebase 或强推。
- 提交信息用英文，标题写改动后的行为。
- 分支与 PR 的格式见 [CONTRIBUTING.md](../../CONTRIBUTING.md)：从 `dev` 拉主题分支，PR 以 `dev` 为目标。
