# 交付与同步流程

适用：改动做完、准备汇报，或用户要求提交、拉取、推送、开 PR。

## 汇报

1. 按 [验证流程](verify.md) 跑完检查。
2. 看一遍最终差异：有没有意外改动、生成文件漂移、私人内容（本机路径、凭据、录制）。
3. 汇报改动后的行为、涉及的文件、实际跑过的验证和结果、没覆盖的范围。到此为止。

## 何时可以动手

- 不主动询问或提议 commit、push、开 PR、合并；用户需要时会直接说。
- 一次授权只覆盖当时点名的那批改动；开始新需求后授权失效。
- 新需求的改动在用户明确验收前，不 push、不开 PR，即使之前授权过。自己跑通测试不算验收。

## 代码与私人笔记一起同步

私人笔记在 `<主目录>/.local`，是独立的 Git 仓库（定位方法见 [文档流程](docs.md#私人资料local)）。
它存在且是 Git 仓库时，代码的每个 Git 动作都顺带处理它；不存在就跳过，不创建、不提示。

| 用户要求 | 代码 | 同时对笔记 |
| --- | --- | --- |
| 提交 | `git add <具体路径>`，`git commit` | 本任务写过的笔记有改动时：`git -C <主目录>/.local add <这些文件>`，`git -C <主目录>/.local commit` |
| 拉取 | `git pull` | `git -C <主目录>/.local pull --ff-only` |
| 推送 | `git push` | `git -C <主目录>/.local push`（远端不能是上游 `kunghim/CoBot`，是就停下告诉用户） |
| 开 PR | 按 CONTRIBUTING | 不涉及：笔记永远不进 PR |

- 笔记拉取不能快进（两台电脑各自改过）时，停下告诉用户，不自动合并或覆盖。
- 笔记里别的会话写的文件不替它提交。
- 汇报时分开写代码和笔记各自提交、推送了什么。

## 代码提交规则

- 只 `git add <具体路径>`，不用 `add -A`、`add .`、`commit -a`；不擅自 reset、stash、rebase 或强推。
- 提交信息用英文，标题写改动后的行为。
- 分支与 PR 的格式见 [CONTRIBUTING.md](../../CONTRIBUTING.md)：从 `dev` 拉主题分支，PR 以 `dev` 为目标。
