# 需求分析与提 Issue

适用：用户在使用 CoBot 时报问题、提需求或丢截图，要分析清楚后提成 Issue，交给编码智能体开发。
这份流程只分析和提 Issue，不写业务代码；产品上的选择由用户决定，智能体给选项和推荐。标签规则见 [Issue 分诊](../reference/triage.md)。

## 流程

1. **拆分**：一条消息可能含几个需求，逐条列出；几条是同一个原因的合成一条，并说明原因。
2. **理解**：分开写「现象」和「用户想要的结果」。一句话需求背后有产品决定的（例如要不要推翻已有约束），先问用户再写。
3. **定位**：读代码找到 `文件:行号`，写明基于 `dev` 的哪个提交；用 `git log -S` / `--grep` 看是不是回归、功能是不是被删过。能便宜复现的以 `dev` 为准，用开发数据根，不碰 `~/.cobot`。
4. **查重**：已有 Issue、开着的 PR、主题分支、stash。需求已在 PR 或分支里的，告诉用户在哪、做到哪；能补进已有 Issue 的，追加「补充」一节，不新开。
5. **写并提交**：按下面的详略和要点写，提交后向用户汇报每条的链接、一句话原因和关联。

## 详略

**小需求**（一处改动、意图明确）直接提交：

```markdown
> 发现来源：人工发现（使用中）；定位：代码分析，基于 `dev` @ <提交>，<是否复现>。

## 现象
## 位置
## 验收
- [ ] ...
```

**大需求**（多处改动、有产品选择或要分步）先给用户看草稿。在上面三节之外按需加「背景 / 已确认的决定」「建议做法」「不在范围内」「待定（实现者判断，写进 PR）」。能独立交付的部分拆成子 Issue，父 Issue 只放总目标和子 Issue 清单。

## 写给编码智能体的要点

- 分清已验证和推测；原因没查实的写「尚未验证」和要先做的确认步骤，标 `status: needs-triage`。
- 写清已有能力和数据（接口、组件、已存的步骤），免得重做；指出必须同步改的文档（如 `docs/product/decisions.md` 的对应条目）。
- 会话区的需求（回合显示、步骤、卡片、状态、输入框、内置浏览器）先写 Codex 怎么做，要求 PR 说明对照了哪些、哪里有意不同。
- 改同一批文件的 Issue 互相链接，写明建议同一分支和先后顺序；依赖其他 Issue 的写明依赖。
- 用户后来补充的意见追加到原 Issue 的「补充」一节，必要时改标题。

## 格式与标签

- 中文正文；标题写现象或期望的行为。
- 类型和模块标签按 [Issue 分诊](../reference/triage.md)。需求明确的加 `status: accepted`。
- 用户发现的不加 `ai-discovered`；智能体自己发现的才加。
- 公开仓库：不写私人路径、账号、密钥、对话原文；截图上传不了就用文字描述。

## 操作备忘

- 提交：`gh issue create --title ... --body-file <临时文件> --label ...`；正文先写在临时目录，不进仓库。
- 互相引用：先建好再回填编号（`gh issue edit <n> --body-file ...`），避免编号写错。
- 挂子 Issue：`gh api -X POST repos/kunghim/CoBot/issues/<父>/sub_issues -F sub_issue_id=<子的 id>`，子的 id 用 `gh api repos/kunghim/CoBot/issues/<子> -q .id` 取（不是编号）。
- 核对 Codex 协议：`codex app-server generate-json-schema --out <临时目录>`，`CODEX_HOME` 指向临时目录；与 `internal/engine/codex/handled.go` 对照。
