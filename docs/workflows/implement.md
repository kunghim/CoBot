# 实现流程

适用：实现功能、修复问题、重构。

## 开始

1. `git status --short` 和当前分支；有不属于本任务的改动就保留，不要顺手处理。
2. 明确预期结果和验收条件，分清：用户明确要求的、你自己的实现选择、还没定的产品问题。
   可逆的实现细节自己决定；会实质影响范围或正确性的缺失信息才问，问的同时继续做不依赖答案的部分。不重复问已经定了的事。
3. 按 AGENTS.md 的路由表读对应规则；改行为前读相关源码、调用方和测试。
4. 需要背景时读主目录 `.local/README.md`（存在的话）引用的方案或讨论；它们可能过时，以代码为准。

## 实现

- 较大的改动先用几句话说明改法和验证方式，再动手。
- 只做任务范围内的事：不顺手清理无关代码、不做推测性抽象、不加新依赖、不加没实现的界面入口。
- 解决根因，沿用周围代码的写法和注释密度；检查受影响的调用方，按需同步契约、迁移、语言包和文档。
- 代码注释写清原因，不引用需求或验收编号。

## 并行与隔离

- 需要隔离时用独立 worktree，核对起始 ref，在返回的路径里工作。新 worktree 先装前端依赖并构建前端（见 [踩坑记录](../pitfalls.md)）。
- 多个会话改同一批文件前先划分范围；并行运行时各用各的数据根。
- 拆给子智能体的工作，检查它的实际产出再整合；“声明完成”不等于做完。

## 收尾

先按 [验证流程](verify.md) 验证，再按 [交付流程](deliver.md) 汇报。
