# CoBot 会话隔离验证（2026-10-14）

## 结论与产品边界

补充边界：本页通过的是会话数据隔离，不代表 Windows 系统沙箱资源相互隔离。重启故障、恢复及当前版本有限共存结果见 [Windows 恢复与共存验证](2026-10-14-Windows恢复与共存验证.md)；整个桌面重启后的命令共存复验已通过，私有官方登录后的真实模型工具仍需独立验收。

**会话隔离、开发/生产隔离及真实对话重启恢复通过。** 给 CoBot 启动的 app-server 使用独立 `CODEX_HOME`，并让 SQLite 状态位于同一私有根，可以保存真实 thread 而不进入日常 Codex 的会话库。正式路径建议为生产 `~/.cobot/engines/codex`、开发 `~/.cobot-dev/engines/codex`；本轮只创建临时实验目录。

**已有登录不会自动继承。** 内存注入现有 ChatGPT 登录的受控实验成功，但本机接口标为内部、不稳定，不能因此把“无缝复用原生登录”标为已确定的首版实现。首版最简单的建议是 CoBot 首次独立官方授权，同一环境内所有团队复用；这是建议，不覆盖用户对登录方式的既有决策。

## 环境与证据

- Windows、本机 `codex-cli 0.161.0`、Node 24.21.0；模型 `gpt-6.1-sol`，提供方标识 `custom`，ChatGPT 登录。
- [`home-isolation.mjs`](../../experiments/app-server/home-isolation.mjs) 为实验程序；[`Client`](../../experiments/app-server/client.mjs) 新增子进程 `env` 参数，既有默认调用保持原行为。
- 成功报告：`.tmp/app-server-spike/home-isolation-1791985381117/report.json`。原始文件留在忽略材料区。
- 临时的 production/development 目录代表两套运行环境；用户选择的团队工作目录与 Codex 状态目录是不同概念。
- 以 `ephemeral: false` 创建 thread，实际完成两次首轮对话和两次恢复对话；不是模拟模型，不使用临时 thread 替代持久化。

## 实测结果

| 检查 | 结果与范围 |
| --- | --- |
| 空的私有目录继承登录 | 不继承，`account/read` 为 `null`，日常目录仍是 ChatGPT 登录 |
| 内存注入既有账号 | 开发/生产均识别为同一个 ChatGPT 账号，无凭据文件副本 |
| 私有对话位置 | 两个 thread 的存储路径分别位于各自私有根 |
| 真实模型对话 | 生产返回 `COBOT_PRIVATE_PROD_7319`，开发返回 `COBOT_PRIVATE_DEV_5297` |
| 关闭进程并恢复 | 同一 thread id 恢复成功，分别记住前一轮标记 |
| 开发/生产列表 | 各自能列出自己的 thread，看不到另一个环境的 thread |
| 日常 Codex 的完整列表查询 | 遍历分页并显式涵盖模型提供方及本轮来源，未出现两个私有 thread |
| 日常目录按 ID 读取 | 无法读取这两个私有 thread |
| 原生应用最近聊天 | 应用工具读取最近 50 条摘要，无这两个 thread；不是全部历史的截图检查 |
| 官方浏览器登录入口 | 私有目录能生成并取消登录流程，没有完成新登录 |
| 凭据落盘检查 | 成功实验结束后扫描 217 个文件，未匹配到源登录的实际 token 值，私有目录没有 `auth.json` |
| 原生日常配置与凭据 | 实验前后 `auth.json`、`config.toml` 摘要一致，文件未修改 |

列表检查不能靠前端隐藏标签：本轮连日常目录按 ID 读取都找不到私有 thread。旧测试会话没有被删除或归档，隔离不会让之前已经写入日常库的记录自动消失。

## 凭据复用的限制

官方说明 `CODEX_HOME` 同时控制 config、auth、sessions 等状态，[环境变量文档](https://learn.chatgpt.com/docs/config-file/environment-variables)；因此单独修改会话根不会自然复用日常目录里的凭据。

本机生成的 `LoginAccountParams` 对 `chatgptAuthTokens` 写明：`[UNSTABLE] FOR OPENAI INTERNAL USE ONLY - DO NOT USE.` 当前[官方 app-server 文档](https://learn.chatgpt.com/docs/app-server#authentication)也将其列为实验性外部 token 模式，需要宿主负责认证生命周期和刷新。

本实验显式启用 `experimentalApi`，只在内存读取已有登录，使用 `cli_auth_credentials_store="ephemeral"`，关闭子进程诊断日志，验证了有效 token 下的四个短 turn。它不证明长期刷新、过期、撤销、账号切换或所有用户都可复用。仅通过 `CODEX_ACCESS_TOKEN` 环境变量的本机探测未使 `account/read` 识别登录，没有把该方式标为已验证可用。

独立官方登录的入口已验证，但没有让用户重新授权，所以“在私有目录完成官方登录后的完整执行”不在本轮通过范围内。正式实现仍需明确选择：独立官方授权，或经过进一步评估的凭据复用方案。

## 实验修正与未覆盖项

初次未登录测试不能完成模型对话，不能当成完整恢复验收；后续改为受控内存认证后的真实对话。独立目录没有原生 MCP 定义，照搬 `mcp_servers.rea.enabled=false` 会创建缺少 transport 的无效配置，现已去除。`thread/list` 默认过滤会受提供方/来源影响，校验必须显式覆盖本轮类型，不能凭空列表断言隔离。

未验证：正式目录/产品实现、macOS/iOS、私有目录中的原生文件与命令工具、多个团队长期并发、登录刷新与系统钥匙串、完整崩溃恢复。既有正常接入证据见[Windows shell 复验](2026-10-14-Windows-shell复验.md)，不把本轮纯对话扩展成全部工具能力通过。
