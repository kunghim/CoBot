# 会话、接力、审批与恢复（真实 Codex）

主链路在 `$R/real`（官方账号）。每条用例记录：用时、使用的模型和供应商（以协议记录或数据库为准，不以模型自述为准）。
规则见 [接力规则](../../product/relay.md)。确认卡和验收卡现在直接出现在会话主区（不再是「展开信息面板 → 任务标签」的浮动卡片）。接口核对走 `/api/v1/questions`（`kind=confirm/acceptance`，决定走 `/questions/{id}/answers`，confirm 卡必须带 decision=accept/revise）；`/api/v1/approvals` 只管原生命令审批和恢复卡。

| ID | 层 | 步骤 | 期望 |
| --- | --- | --- | --- |
| C7 | 冒烟 | **第一个需求**：让项目经理做一个小改动，例如给 README 追加一行，走完 确认 → 实现 → 验收。工作目录可以不是 Git 仓库，此时工程师会按规则提问，回答后继续 | 一次走通；链路和改动大小相称（小改动 3 环，不塞设计与评审）；确认卡有需求文档、验收标准、链路图；改动只有需求要求的内容；验收卡 `status=open` 等人决定；卡片链可在数据库里看到；项目目录里会多出 CoBot 的标记文件，属于正常，测完在记录里注明 |
| D1-1 | 回归 | 完整链路：一个带测试和评审的小功能。测试环节手动在页面里埋一个缺陷，让测试退回 | 测试工程师用团队浏览器复现并退回；工程师返工；复测、评审通过；验收卡写明修复情况 |
| D1-2 | 回归 | 让工程师在团队目录外写文件，触发原生审批；在页面上批准一次、拒绝一次 | 审批卡显示命令、目录、理由和四个按钮；批准后文件写入；拒绝后命令没执行，成员如实回报 |
| D1-3 | 回归 | 需求说得含糊，让项目经理提问 | 出现提问；回答原样写进需求和链路 |
| D1-4 | 回归 | 确认卡上要求修改 | 修改写进需求，回到确认卡 |
| D1-5 | 回归 | 运行中取消需求；另一个需求运行中打断，再发一句转向 | 取消：1 秒内运行被打断，需求变 cancelled，成员空闲。打断：运行 interrupted，需求仍进行中，转向内容被做进去 |
| D1-6 | 回归 | 制造一次失败（例如在 `$R/gw` 里给成员选一个网关不提供的模型），然后点「重试这一轮」 | 失败原因可理解；换回可用模型后重试成功；已取消卡片的轮次不能重试 |
| D1-7 | 回归 | 运行中强杀核心进程，重启。恢复卡上分三次依次试「重跑」「只释放成员」「放弃」 | Codex、MCP 桥、浏览器跟着退出，没有遗留进程；每个选项的行为和卡上说明一致 |
| D1-8 | 回归 | 两个团队同时各跑一个需求；协作链预算设为 2，分别选「继续」和「停止」 | 两边互不干扰，各有自己的浏览器 profile；「停止」后这一环成员的会话里写明停在哪、怎么继续，不唤醒任何人 |
| D1-9 | 回归 | 观察：一轮结束卡片没交接的情况（网关模型较常出现） | 出现过就核对：第一次在原会话提醒；第二次换新会话再提醒；之后留给用户。没出现就写「未触发」，不强求 |
| D1-10 | 回归 | 取消需求时带上过期的版本号（`POST /api/v1/requirements/{id}/cancel`，`If-Match` 里放旧版本）；再不带版本号取消 | 版本已变时按冲突拒绝；不带版本号照常取消 |
