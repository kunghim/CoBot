# 发布前实测

适用：候选版本（`origin/dev` 最新提交）在合并 `main`、打包发布之前，由一个专门的会话安装并逐项实测。
目标是这个会话不用重新了解项目：怎么用在 [操作指南](guide.md)，测什么在 [cases/](cases/)，这次要测哪些由脚本算出来。

## 流程

1. **算出这次要测什么**：`node scripts/live-test-plan.mjs`。
   - 输出三段：要跑的用例（冒烟、变更触发、从未测、上次未通过）、沿用上次结果的用例、两个版本之间合并的 PR 标题。
   - 「需要人工归类的文件」不为空时（退出码 2），先到 [areas.json](areas.json) 把这些文件归到某个功能区、`shared` 或 `exempt`，再重新运行。不能默默放过。
2. **读一次** [操作指南](guide.md)，再只读「要跑」里涉及的 `cases/<功能区>.md`。不需要读源码；对某个 PR 有疑问时，读它的 diff，不要通读。
3. **构建候选版本、准备数据根**：按指南第 2、3 节。
4. **执行**：先跑 [门禁](cases/gates.md)，再跑要跑的用例。真实 Codex 会话是正常消耗，照常跑。
5. **写记录、更新账本**：记录写进 `.local/validation/`，账本用 `live-test-plan.mjs mark` 更新（指南第 7 节）。
6. **汇报结论**：能否进入下一步，不能的话还差什么。合并 `main`、触发打包、公开发布由用户决定。

## 开发过程中怎么用

这套用例和指南也给开发中的验证用：`node scripts/live-test-plan.mjs touched` 按当前改动列出涉及的功能区和对应用例，不需要账本，细节见 [验证流程](../workflows/verify.md#开发中在真实应用里验证改动)。它不替代 `scripts/check` 和自动化测试，也不做整轮实测。

## 为什么不是每次全测

脚本拿账本里每条用例上次通过的提交，和候选提交做 `git diff --name-only`，按 [areas.json](areas.json) 把变更文件归到功能区：

- 功能区里有文件变了：这个区的用例到期。
- 冒烟用例：每次都跑，兜住共享代码的间接影响。
- 从未测过、上次没通过的：到期。
- 其余：沿用上次结果，记录里写「沿用 `<提交>`」。

需要整体重来时加 `--full`（比如隔了很多版本，或大重构之后）。

## 文件

| 文件 | 内容 | 谁改 |
| --- | --- | --- |
| [guide.md](guide.md) | 怎么装、怎么启动、东西在界面哪里、怎么验证、怎么记录 | 流程变了才改 |
| [areas.json](areas.json) | 功能区、源码路径、用例文件的对应表 | 加了目录或功能就改 |
| [cases/](cases/) | 每个功能区的用例，ID 稳定 | 功能变了就改 |
| `.local/validation/live-test-ledger.json` | 账本：每条用例上次的结果和提交（私有） | 每次测完 |
| `.local/validation/*-live-test-record.md` | 每次的测试记录（私有） | 每次测完 |

## 维护

- **改了界面或行为的 PR，同步补用例和对应表**：新功能加到对应的 `cases/*.md`，新目录加进 `areas.json`。`scripts/check-docs.mjs` 会检查每个已跟踪文件都归了类，没归类就让 CI 变红，这是防漏测的关键。
- 用例 ID 不要改、不要复用；删用例前先在记录里说明。
- 用例表格的列固定为 `ID | 层 | 步骤 | 期望`，层是「冒烟」或「回归」，脚本按这个格式读取。
- 测试记录和账本含本机和账号信息，不进仓库。
